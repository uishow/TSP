一、现象

回测进行时前端报错：backtest worker exited without result (exitcode=-9)。

退出码 -9 = 进程被 SIGKILL 信号杀死。在容器里，这几乎总是 内存耗尽（OOM） 被系统 OOM Killer 杀掉，而非代码异常或崩溃。

二、根因：OOM（内存超限）

资源 / 配置问题 回测 worker 是独立 spawn 子进程；当它占用的内存超过容器硬上限时，cgroup / 主机 OOM Killer 直接 SIGKILL（exit −9）。

本机实测资源约束：

项数值说明
Mac 主机总内存48 GiB机器实际有 48 GB
Docker Desktop 内存上限7.747 GiBDocker 被分配的额度（默认偏小）
TSP 主进程常驻~2.3 GiB容器空闲时 docker stats 实测
worker 可用余量≈ 5.4 GiB7.747 − 2.3，超过即触发 OOM
触发负载：用户跑的是 全市场股票回测（asset_type=stock，不传 symbols 即全 A 股约 3000+ 只，窗口 2026-01-01→2026-11-07 共 11 个月，mode=position）。把全市场日线 + 衍生特征一次性装进 worker 矩阵，内存远超 5.4 GiB 余量 → OOM。

三、为何 TSP 自带的「回测内存上限」没拦住

TSP 有一个软上限（backtest_worker_rss_limit_gib，默认 6 GiB）：worker RSS 超过该值会被 TSP 主动终止并给出友好中文提示（"回测任务内存超过上限…可在 设置→系统设置→性能与内存 调高「回测内存上限」"）。

但该软上限（6 GiB）高于容器实际能提供的余量（≈5.4 GiB）。于是 cgroup OOM Killer 在 worker 触达 6 GiB 之前（约 5.4 GiB 处）就已 SIGKILL，TSP 的 2 秒轮询来不及介入 → 落到用户眼前的就是原始 −9 而非友好提示。

四、与本次「财务概括」修复无关

已核对 本次 −9 发生在策略 ai_mw60ksjw（asset_type=stock）全市场回测上；而前一轮修复只动了：

  • overrides/financials_metrics_enrich.py（财务指标/股本 运行时换算，仅 /api/financials 路径）；
  • data-local/strategies/custom/custom_simple_ma_cross.py（给均线交叉策略补 params）。

二者均不进入股票回测内存路径。git diff 仅含 bridge/local_store.py 与 overrides/bootstrap.py 的历史改动。故 −9 不是回归，是回测负载本身的资源问题。

六、修复 / 缓解（三选一）

方案 A（最推荐）：提高 Docker Desktop 内存额度

主机有 48 GiB，但 Docker 只拿到 7.747 GiB。在 Docker Desktop → Settings → Resources → Memory 调到 16–24 GiB 后重启 Docker，全市场股票回测即可获得足够内存跑通。这是从根本上解决「全市场回测」的方案。

方案 B（不改 Docker）：缩小回测范围

不传全市场，改为：① 传显式 symbols（自选/关注的一篮子，几只到几十只）；或 ② 收紧 basic_filter（更少板块 / 更高 float_cap_min / 更窄价格带）；或 ③ 缩短日期区间（如一个季度）。实测 6 只 × 2 个月仅 12 KB 矩阵、0.4s 完成。

方案 C（防再次「裸崩」）：设优雅内存上限

把 TSP「回测内存上限」调到 ≈4 GiB（低于 5.4 GiB 余量），或在 .env 设 TICK_WORKER_RSS_LIMIT_BYTES=4294967296。这样超内存时 TSP 会给出中文友好提示而非 −9，便于判断是「该缩小范围 / 加内存」。注意：此方案只让失败更清晰，不会让全市场回测凭空跑通。

三态标注：本 −9 属资源/配置问题（非代码缺陷），小范围回测已实测跑通；全市场回测因 8 GB 级容器内存不足而 OOM，按方案 A/B 解决。
