#0 · 先读这一页：三态、边界与诚实原则

这份手册最重要的一句话

「接口返回成功」「文档写了这个功能」「回测跑出一条漂亮曲线」，是三件完全不同的事，任何一件都不等于「这套策略能赚钱」。本手册全程把这三种状态分开标注，禁止把上游设计稿写成已实现功能，禁止把 HTTP 200 写成业务可用，也禁止把本机七星175 的回测数字写成实盘业绩。

0.1 三态徽章（全文通用，看到徽章先判状态）

上游文档 / 设计提案

本机仅冒烟 / 未验证
只读接口返回 200、有真实数据，或源码 / 契约静态核对过，但没发起过完整写操作或交互。例如因子 validate/trial、优化折预览、模拟盘下单成交闭环、UI 点击。

0.3 谁是读者，怎么读

本手册面向产品负责人（非技术背景）。因此每个机制的顺序固定为：

  1. 它在解决什么问题 —— 先讲业务风险，不讲实现；
  2. 怎么操作 —— 点哪里、调什么、给什么命令；
  3. 结果在哪看 / 出错怎么查 —— 落盘路径、返回字段、报错原文。

唯一的例外是 §3 技术契约 与 §11 SOP 命令：这两节允许给精确字段、代码块和命令，供你转交给工程同事执行。看不懂代码不影响判断体系是否成立 —— 你只需要盯住每节的「结果在哪看」和「盈利前的检查清单」。

#1 · 从「想法」到「可盈利体系」的六道闸门

它在解决什么问题

大多数人亏钱不是因为策略不够聪明，而是把「回测曲线好看」直接当成了「可以下单」。中间缺的是一层层会拦住你的闸门：先证明没偷看未来，再证明参数不是碰运气，再证明换一段行情还行，再证明发布后没退化，最后才轮到真金白银。可盈利体系 = 一条能被反复证伪、且每次证伪都有留痕的流水线，而不是一条净值曲线。

把 TSP 的能力按「闸门」重排，而不是按菜单重排，是这样六道：

1.1 每道闸门的「通过判据」与「本机现状」

1

想法 → 定义：先锁死口径，再谈收益

怎么操作：用 §2 三种方式之一写成一个带 META 的策略文件，明确 asset_types、timeframes、参数默认值。结果在哪看：GET /api/strategies?asset_type=etf 应返回 strategies=1、load_errors=[]。

出错怎么查：策略页空白多半是「默认停在股票」——本机股票策略数为 0，前端 useState("stock") 写死，必须手动切到「ETF」。这是设计限制，不是故障。

2

历史验证：证据链比收益率重要

怎么操作：正式回测（非优化器内的轻量试算）会自动生成 证据链。结果在哪看：data-local/backtest_runs/{run_id}.json 里的 lookahead.status、execution_timing.status、reproducibility_sha256、limitations。

通过判据：本机七星175 的证据链 lookahead=passed、execution_timing=passed、differences=0 —— 说明代码与引擎层面没发现未来函数。但这只是「引擎抽查通过」，不等于无偏，见 §5.4。

3

稳健性：别信单一历史冠军

怎么操作：§6 的 K 段稳健优化（稳健分 0.6×中位 + 0.4×最差）+ 滚动样本外检验。结果在哪看：稳健优化结果面板的排名表、冠军卡、高原视图；GET /api/backtest/optimize-robust/preview 看分段。

本机现状：曾因 ETF 历史被截断到 244 天，选 2025-01-01~2026-11-05、K=4 导致 624 组全失败；补齐到 2020 起的历史分区后原样重放得 612/624 成功。区间不要早于 2020-01-02。

4

挖掘与发布：自动只到「候选」为止

怎么操作：§7 的挖掘 → 保存（promote）→ 显式发布（publish）。铁律：自动任务只生成 pending 候选，永远不会自动发布策略；发布在服务端强制校验证据门槛。

本机现状：历史 2026-11-04 那次 failed 已定位为 enriched 备份分区重复 (symbol,date) 键（2348 组 / 3374 多余行），触发上游 mining_runtime.py:386-401 的 invalid_key 检查；数据修复后现役 245 个分区共 1,340,852 行、null 0 / 重复 0 / invalid_key=False。本轮端到端重跑 POST /api/backtest/mining/runs（exploratory、4 因子、80 只真实标的、2025-12-10~2026-11-06）得到 run 827e0f10ef5a4df98c94057e33cce2e9 succeeded，四个 artifact 全部落盘，/api/backtest/lab/report 的 mining.last_run 已刷成 succeeded —— 链路端到端跑通。但必须诚实：candidate_count=0、valid_fold_count=0、skipped_fold_count=1、confidence=low，没有任何可发布候选；exploratory 档按上游只能进 pending 且永远不能发布，发布门槛六项一条都没走到；balanced / strict 因股票日线仅 245 根（trading_bars=245，需 786 / 1164）仍 eligible=false。因此仍不能声称「自动挖掘可产出可发布策略」，详见 §7.10。

5

发布后守成：让「退化」自己报警

怎么操作：策略守护档案 healthy / watch / retired 三态 + 模拟盘跟单。结果在哪看：data-local/user_data/strategy_guardian/{strategy_id}.json 与守护页。

本机现状：strategy_guardian/ 与 strategy_overrides/ 目录均为空，守护复验与「应用冠军参数」尚未产生任何真实档案；模拟盘下单成交闭环未端到端验证。见 §9。

6

真实执行：最后一道由人把关

怎么操作：监控中心按 T 日收盘信号出票 → 人工在券商按信号下单，或把原聚宽 / QMT 版本接回 QMT 实盘。结果在哪看：/monitor 触发记录、/api/alerts、券商成交回报。

硬边界：TSP 没有券商下单接口，/paper 是纯虚拟撮合。七星175 源码来自「七星超级175聚宽v3.141-qmt」——那份是可接实盘的版本，TSP 这份是移植的研究 / 验证版本，不要混淆。

给产品负责人的一句话判据：任何时候有人拿一条净值曲线来汇报，先问三个问题 —— 证据链的 limitations 写了什么？样本外哪几段？发布后有没有守护记录？三个问题答不上来，这条曲线就还停在闸门 2，不能往下走。

#2 · 策略的三种扩展方式，以及该选哪种

它在解决什么问题

「我有一个想法」到「引擎能跑」之间，成本差别极大。选错扩展方式，要么把简单筛选写成几百行 Python，要么把需要状态机的复杂轮动硬塞进表单。这一节只做一件事：让你在动手前先选对档位，避免用最贵的方式解决最便宜的问题。

上游文档说明 以下三种方式来自 strategy.md「扩展策略的三种方式」，是上游仓库的功能说明；本机只对其中的方式三做过端到端实测。

2.2 选择建议（给不写代码的人看的决策表）

如果你的想法是…选理由 / 别踩的坑
「挑出 RSI 超卖且放量的票」这类一两个条件① 自定义信号表单即可，热加载，不用碰文件；写成 Python 是杀鸡用牛刀
「帮我写个均线多头策略，但我不想学语法」② AI 生成生成后默认是研究草稿，必须显式发布才加入正式策略池；AI 只负责代码，回测验证与上线决策永远由人完成
「26 日加权对数回归动量 + 双风险规避四格池 + 每日轮动 1 只」③ 代码编写表单表达不了带状态 / 带矩阵的打分；只有 matrix_native 能给出 score 与全量 exit 语义
「把聚宽 / QMT 上跑过的策略搬过来」③ 代码迁移先做移植取舍清单：分钟级守卫、溢价率、停牌、精确成交时点往往无法表达，必须写明「未移植」，见 §4.4
「完全自动赚钱，我不管」不存在上游明确不做 AI 荐股 / 涨停预测；挖掘也只产出 pending 候选，不自动上线

2.4 策略池、草稿与资源包：三个容易混淆的概念

  • 策略池：按「策略库 / 已选列表」组织，可搜索名称、ID、描述，按来源与周期筛选；只有点「保存策略池」才应用选择。清空后可「撤销清空」，也可「还原」打开窗口时的选择。保存后的选择与顺序同步到界面偏好，重启或端口变化后可恢复。
  • 偏好 ≠ 运行入口：本机实测 七星175 已在 ui_prefs.strategy_pool 里，但筛选页资产类型不匹配时，引擎按 asset_type in meta["asset_types"] 直接把策略过滤掉 —— 策略池里有，不等于列表里看得见。
  • AI 草稿：生成后仍是草稿，发布立即生效，但「加入池」仍须另行保存。AI 生成的 .py 未声明发布状态时默认导入为草稿。
  • 资源导入与批量导出：策略 / 因子 / 信号页顶部小盒子图标进入「设置 → 导入与备份」；统一接口 /api/definitions/resources（GET 查询、POST /export/preview / /export / /inspect / /apply）。导出 ZIP 含策略源码、已保存调参、引用信号 / 因子及递归依赖；同 ID 内容相同自动复用，内容不同须逐项确认替换，不自动改 ID、不静默覆盖。资源包不含行情、缓存、账号或密钥。

matrix_native 策略的进出场信号由策略自己计算，signal_factor_rank_entry / signal_factor_rank_exit 只是输出标签，无需在信号库创建同名定义；打包与预检也不把它们当外部依赖。

#3 · 策略文件结构与 matrix_native 契约

它在解决什么问题

#4 · 信号、过滤、排序、持仓与出场语义

它在解决什么问题

「给每只 ETF 打个分」和「今天到底买卖哪只」之间，还隔着过滤、排序、持仓上限、出场四层语义。历史上最贵的一个 bug 就出在出场层：源码注释记录了一笔持仓曾卡住 194 个交易日直到回测结束，原因就是「只给策略自己认为的昨日目标发 exit」与引擎实际持仓错位。这一节把每层语义讲清楚，让你能判断一条出票结果是不是合理。

全部来自本机实测源码，并以 2026-10-30 ~ 11-06 的真实出票结果收尾。

4.1 五步流水线（七星175 每天做的事）

1

打分：26 日加权对数线性回归

解决什么问题：不只看涨了多少，还要看涨得「稳不稳」。做法是对 window = lookback_days + 1 = 26 根 log(close) 做加权线性回归，权重 w = np.linspace(1.0, 2.0, 26)（越近端权重越大，与原版一致），得分 = 年化收益 × 加权 R²，其中 annualized = exp(clip(slope*250, -50, 50)) - 1，R² = 1 - ss_res/ss_tot 并裁剪到 [0,1]。趋势不稳（R² 低）会被自动扣分。

只用 ≤ t 的收盘价，按 t 对齐，天然无未来函数。

2

过滤：六道候选门槛

解决什么问题：把「得分高但正在暴跌 / 刚破位 / 数据不完整」的标的挡在外面。源码里 ok 是以下条件的按位与：

条件默认阈值挡掉什么
window_valid26 根全 finite停牌 / 数据缺口
r2_all >= r2_min0.35上涨不平滑、忽上忽下
no_crash近 3 日每日 ratio >= 0.97单日跌幅 > 3% 的急跌
short_ok10 日短期动量 >= 1.0短期已转弱
score >= buy_min 且 <= rank_max0.20 / 10000.0得分过低或异常值
trend_ok（可关）price > ma10 且 ma5 > ma10均线空头结构
pool_ok四格池掩码不属于当前市况允许的池
3

风控：双风险规避「四格池」

解决什么问题：A 股弱、海外也弱的时候，不该还满仓买股票。策略用矩阵内宽基 ETF 代理判断「A 股弱 / 海外弱」两个布尔量，再决定今天允许从哪个池里选：

A 股弱海外弱允许池业务含义
否否ALL_POOL（海外 + 商品 + A 股，52 只）正常市况，全池选最强
否是DOMESTIC + COMMODITY海外弱，回避海外 QDII
是否OVERSEAS + COMMODITYA 股弱，回避 A 股
是是COMMODITY（7 只商品 ETF）双弱，只留商品避险

代理：A 股弱看 510300/510500/510050/159915/588080/512100 六只，现价<MA10 或 MA5<MA10 死叉计数 >= 3/6；海外弱看 159509/513500/513400/513520 四只，计数 >= 2/4。用矩阵内代理而非外部指数，好处是完全在 market 矩阵内按 t 对齐、不依赖 get_index_daily 的默认 end=today。

4

排序与持仓：每日 top1

rank_score = np.where(ok, score, -1.0) → best = np.argmax(rank_score, axis=1) → 只有 rank_score > 0 才算 has_pick。持仓 1 只（META.limit=1、回测 max_positions=1、position_sizing="equal"），非目标标的全部置 exit，实现每日轮动。

弱市空仓是设计内行为：enable_defensive_etf=False，没有合格标的就 has_pick=False，当天不发入场信号。11-05 / 11-06 的 total=0 不是接口故障。

5

出场：必须「全量覆盖非当日目标」

解决什么问题：源码注释写得很直白 —— 回测按 T+1 开盘成交且有 max_positions 限制，引擎的实际持仓与策略「上一日 top1」会错位；若只给策略自己认为的昨日目标发 exit，引擎实际持有的标的可能永远收不到卖信号（实测一笔持仓卡了 194 个交易日直到 end）。

entry = np.zeros((rows, cols), dtype=np.uint8)
entry[row_ids[has_pick], best[has_pick]] = 1
# 轮动退出必须覆盖「全部非当日目标」的标的
exit_ = (1 - entry).astype(np.uint8)

回测引擎只对持仓标的消费 exit，所以多出来的信号不影响交易正确性；代价是扫描页会列出未选中标的的卖出候选（本机口径收敛后 exit_signal_hits 为 51/52，收敛前是 1695 条噪音）。

4.4 移植取舍：明确「未移植」的部分（别以为功能齐全）

#6 · 稳健优化、滚动样本外与护栏

它在解决什么问题

原来的「参数优化」在用户选定的整段区间上对每组参数回测、按单一目标排序 —— 排名其实是「对这段历史噪声的拟合度排名」，选出的必然是尖峰参数，未来失效是设计使然。这一节的两套新协议，分别回答两个不同的问题：哪组参数靠谱（稳健优化），以及这套「选参数的流程」本身靠不靠谱（滚动样本外检验）。

关于上游状态标注的一个诚实提示：robust-optimizer-plan.md 开头写「状态：设计已定稿，待实施（P1–P4）」，而 auto-strategy-lab-plan.md 写「P1 / P2a / P2b / P2d / P3 均已实施并通过真实数据 E2E 验证」。两份上游文档的状态标注并不一致。本机可确认的事实是：/backtest?tab=robustness 里稳健优化与 walk-forward 的 SSE 能跑到 done，折预览与区间提示可用；但这不等于上游 P1–P4 的全部设计都已落地。本节讲的是协议口径，具体按钮以你眼前这一版面板为准。

6.2 稳健优化 · K 段锚定验证 + 两阶段预算

区间 [S,E] 上的评估协议：

  1. 切窗：等分为 K 个互不重叠验证段 V₁…V_K（默认 K=4，可配 3–6）。每组参数固定不变地在每个 Vᵢ 上独立回测（复用 walkforward 折工具 + prepare_matrix_optimization 矩阵缓存）。
  2. 稳健分：R(p) = 0.6 × median(oos₁…K) + 0.4 × worst(oos₁…K) —— 中位数扛单段运气，最差段惩罚「只在一段行情好用」；各段得分与离散度并排展示（离散度本身就是过拟合警报）。
  3. 两阶段预算：阶段一全网格只跑 K 个短验证窗（总数据量 ≈ 一次全窗，计算量与旧版持平）；阶段二仅 Top-20 跑全窗 IS 得分（算 IS→OOS 退化率）+ 邻域细化。
  4. 免费诊断：阶段一持有「每组 × 每段」完整得分矩阵 → 各段冠军收敛度直接可得。各段冠军收敛 → 参数可信；散落 → 策略本身参数不稳定，任何「最优」都别信。
  5. 高原判据：冠军周围网格点的得分衰减率（数据来自阶段一，零额外计算）。

#7 · 挖掘口径、证据门槛与「永不自动上线」

它在解决什么问题

自动搜索几百上千个因子组合，必然能挑出一个「历史上特别好看」的 —— 这叫多重检验，挑出来的多数是运气。挖掘模块的全部设计，都是为了让「候选」和「可用策略」之间隔着一道服务端强制、按证据计算、人显式确认的门槛。同时它还必须保证：搜索过程本身没偷看未来数据。

上游文档说明 口径来自 mining.md 与 auto-strategy-lab-plan.md。本机链路已端到端实测：历史 11-04 的 failed 已定位为重复键，数据修复后本轮 exploratory 复跑 succeeded（run 827e0f10ef5a4df98c94057e33cce2e9）、战报已刷新、四个 artifact 落盘（见 7.10）。balanced / strict 因 245 交易日不足仍不可用、守护与组合闭环未验证：candidate_count=0、valid_fold_count=0、无任何可发布候选，发布门槛六项一条都没走到。读下面的口径时请同时记住：链路能跑通 ≠ 自动挖掘能产出可发布策略。

7.1 时间与收益口径

  • 全局交易日标签：1 / 3 / 5 日 forward return 都按全局交易日轴精确连接；停牌或缺行不会把「下一条标的数据」误当成下一交易日。周频用每个 ISO 周的第一个实际交易日，月频用每月第一个实际交易日，节假日不会导致整周漏掉调仓。
  • T-1 市场环境：交易日 T 只能使用上一交易日已经得到的环境标签 T-1。统计与挖掘口径聚合为三档：strong = strong + lean_strong、range = range、weak = lean_weak + weak。
  • 两种口径别混：策略回测的环境过滤按原始五档匹配（勾「强势」只允许 T-1 为 strong 的交易日入场；需要三档口径时必须同时勾「强势 + 偏强」）；挖掘内部的 strong/range/weak 拆分按上面三档聚合实现（显式枚举原始状态），两者互不影响。
  • fail-closed：正式区间缺少前驱交易日或前驱环境时直接失败，不会用当日环境、最近自然日或默认环境补齐。
  • 成交和成本：候选策略沿用现有回测撮合规则，包括 T+1、佣金、卖侧印花税、滑点以及涨跌停不可成交约束。因子统计中的 long-short spread 仅用于衡量因子区分能力，是理论价差，不表示 A 股可执行卖空。

财务因子（pb_latest / roe_latest 等 7 个）采用严格点时口径：因子值只在晚于公告日的交易日生效（公告多在盘后，保守取公告次一交易日起），同一报告期以最新公告为准；无财务数据的标的、公告前日期一律为空值并从当日截面剔除，绝不填 0；本地完全没有财务数据时因子回测直接返回明确错误而不是全空结果。

7.2 防未来数据：嵌套 walk-forward

挖掘使用嵌套 walk-forward，而不是「在完整样本上选择后再报告同一段表现」：

  1. 每个 inner 训练折独立学习方向、计算统计、相关去重和组合搜索；
  2. inner test 只用于选择候选，不参与该折的训练计算；
  3. 选择完成后在完整 outer train 上重新训练；
  4. outer test 只进行一次最终样本外评估；
  5. 训练和测试之间保留 purge 与 embargo；默认 purge 为 30 个交易日（auto-strategy-lab-plan 现状表还记录内层 252/63/63、purge 30 + embargo 5）。

任何 fold 缺数据、缺 T-1 环境或不能可靠撮合时都记录为 skipped 并给出原因，缺失指标返回 null，不会显示为 0。

7.3 候选证据口径：三类行，别把「有效折」当样本量

run 级的「有效折」统计只描述因子赛道：它按每折被选中的候选聚合，不是任何单个候选的样本量。单个候选的逐折证据由 folds.parquet 的 evaluation_kind 区分三类行：

类型含义
selected该候选在该 outer 折经 inner 验证胜出后的 outer 测试结果
cross该候选的定义在其他折胜出后，在本折补评的跨折结果。胜出定义会在所有 outer 折上评估，使单个候选的证据不再依赖「它恰好在哪里获胜」
benchmark对照策略在该 outer 测试窗的独立评估，与因子赛道成败无关；即使因子赛道在某折没有任何候选完成内部验证，对照行仍会写入。对照策略是固定定义，不需逐折重拟合，每个 outer 折只评估一次；预算耗尽时写入带原因的 skipped 行，不会静默缺失

探索档（exploratory）结果固定为低置信度，只能保存为 pending 候选。

7.4 晋级与发布门槛（服务端强制）

保存（promote）始终允许，结果进入研究候选库 pending 状态。发布（publish）在服务端强制校验以下证据门槛，不满足即拒绝并返回原因列表：

#门槛阈值
1非探索档置信度exploratory 运行产生的候选不能发布
2有效 outer 折至少 2 个
3正收益折比例不低于 2/3
4样本外 Sharpe不低于 0.5
5最大回撤不劣于 -25%
6样本外交易数不低于 60

门槛按 artifact 行指标在读取时计算，不改变历史 artifact 的 schema，因此旧运行的候选会得到相同的门槛判断。工作台会在候选上显示「达标 / 未达标」标记，未达标候选的「显式发布」按钮被禁用并展示原因。strict 档（confidence=high）在 oos_worst_sharpe 列存在时额外要求最差折 Sharpe > 0。

7.6 任务与资源隔离（长任务不会因关浏览器而丢）

  • 挖掘通过 spawn 子进程执行，不在 FastAPI 请求线程、实时行情回调线程或浏览器连接生命周期内运行；浏览器断开不会取消任务，刷新后可通过持久 run ID 重连；取消请求进入 cancelling，界面应等待后端进入终态。
  • 共享重任务限流容量为 2：普通回测、优化、walk-forward 和矩阵预热占 1，挖掘独占 2 —— 一个挖掘任务不会与另一项大矩阵计算并发。
  • 当前 run store 和 limiter 使用进程内锁：生产环境必须只启动一个应用进程负责挖掘；多 worker Uvicorn 部署不能保证跨进程单飞、事件追加和容量限制。要支持多进程，必须先增加 OS 级文件锁或外部任务协调器。
  • .mining_process.lock（POSIX flock / Windows 字节锁）保证同一时刻只有一个应用进程负责挖掘；持锁者记录 PID、进程创建时间、取得锁的时间和角色，操作系统锁仍是唯一事实。撞锁时面板以降级模式运行，手动 / 自动挖掘和取消入口拒绝修改其他实例的任务，周度挖掘跳过。
  • 挖掘页始终提供「检查并恢复挖掘」按钮：当前后端已持锁时纠正状态；锁已空闲时重新获取；其他实例仍持锁时只显示诊断，不结束进程、不删除锁文件。只有「持有者身份可核验、进程存活、无进行中的挖掘运行、挖掘存储至少 10 分钟无写入」四条全满足，才显示独立的「强制停止并接管」，且用户确认后再次核验 PID 与进程身份。
  • 每个运行目录包含 manifest、compact summary、最近 256 条事件和四个 Parquet artifact；大面板、完整矩阵对象和逐折宽结果不会通过 worker IPC 返回。

7.7 自动运行：只到 pending 为止

  • 周度自动挖掘默认关闭，只允许 balanced 或 strict。启用后，在北京时间配置工作日及其后的同周工作日、日线 enriched 刷新和环境更新成功后尝试入队；配置日的数据流水线失败，后续工作日可以补跑。
  • 同一 ISO 周使用确定性的 claim，只触发一次。已经生成运行记录的失败或 skipped_prerequisite 仍会占用该周 claim，不重复消耗资源。
  • 数据或 T-1 环境覆盖不足时会生成可见的 skipped_prerequisite 运行，不会静默降级到 exploratory。挖掘失败不改变已经成功的日度数据流水线状态。
  • 自动任务只生成 pending 结果，永远不会自动发布策略。
  • 闭环编排（P3）：lab_schedule.run_scheduled_lab 为调度单入口（周度挖掘 + 日度守护，失败互不阻断）；状态机 idle → screen → mine → gate → publish → watch → retire → idle；名额上限默认 10，满时新冠军停在 pending 候选等位；retired 不自动删文件，腾名额走人工归档 / 删除既有路径。数据流纪律：守护层（发布后数据）绝不反馈进取参加权。

7.8 保存与发布：客户端能提交什么

保存候选只从服务端已注册的 candidates.parquet 读取定义，并重新校验 artifact schema、canonical signature、原始请求中的因子 / 策略范围和当前策略兼容性，再写入研究候选库。客户端只能提交 run ID 与 candidate signature，不能在保存时重交权重、方向、公式或代码；保存按 (origin_run_id, candidate_signature) 幂等。

发布是独立的显式动作：

  • 已有策略候选返回原策略 ID，不复制或覆盖源文件；
  • 因子组合候选由服务端根据 run ID 与 candidate signature 派生独立策略 ID；不同 run 即使得到相同组合，也会生成互相独立的策略文件；
  • 发布过程执行 AST/META 校验、create-only 原子写入、引擎 reload、策略缓存失效和监控状态失效；reload 或运行时失效失败会回滚首次创建的新文件；
  • 发布不会修改共享 factor_rank_research 源码或 override。
发布仅表示把固定候选变成可使用策略，不代表样本外表现会在未来持续。这句话是本节的落点，也是整个「挖掘 → 发布」闸门和「真实盈利」之间的分界线。

7.9 性能口径（上游实测，仅供参考，不代表所有数据规模）

#8 · 因子平台：两线模型、表达式层、宇宙与风险调整

8.3 【设计】表达式层 L-DSL：语法、算子与编译期红线

表达式 = expr ::= operand | expr op expr | func(expr[, expr[, const]])，中缀 + 函数调用，无变量赋值、无循环。操作数：基准列（open/high/low/close/volume/amount/turnover_rate/prev_close/raw_close）、白名单指标列、已注册因子 id（递归内联展开）、数值常量。

类别算子
时序（over("symbol")，窗口 n ∈ [2,512]，全部只向后看）ts_mean / ts_std / ts_sum / ts_max / ts_min / ts_delta / ts_delay / ts_rank / ts_zscore / ts_corr / ts_cov / ts_quantile / decay_linear
截面（按日期分组，逐日横截面）rank(x)（横截面百分位 ∈ (0,1]，null 不参与）、zscore(x)（σ=0 → null）、winsorize(x,k)（截尾至 μ±kσ，k ∈ [1,6]，默认 3）
算术 / 工具+ − * /（除零 → null）、log / abs / sign / sqrt / min / max / power(x,c) / clamp(x,lo,hi) / if_else(cond,a,b)、比较与逻辑 > >= < <= == != and or not

v1 不提供 ts_argmax/ts_argmin：Polars 无向量化实现（rolling_map 为逐窗 Python 回调，违反向量化约束），确有需求再经 numba 扩展。

编译期全部强制的校验规则：

  1. 标识符必须在基准列 / 白名单 / 已注册因子内，否则报错（防注入）；
  2. ts_delay / ts_delta 的 n ≥ 0；任何窗口 n ∈ [2,512]；power 指数 |c| ≤ 4；AST 深度 ≤ 12；token 数 ≤ 200；
  3. 常量折叠后产生静态除零 → 编译失败；
  4. 依赖列集合递归展开；warmup_bars = max(各 ts 算子窗口)；
  5. 产出类型必须为数值或布尔；
  6. 禁止未来引用的总闸：所有时序算子 shift 语义已内建，语法层不存在负 shift；code review checklist 补「新增算子必须只向后看」。

编译流水线：text → tokenizer → Pratt 解析 → AST → 语义检查 → 依赖/预热推导 → Polars Expr 工厂；编译失败返回结构化错误（位置 + 原因），不抛裸异常。错误码 E001–E016 是编译与运行校验的唯一错误词汇表，其中 E005 = 负 shift（ts_delay/ts_delta 的 n < 0，负数即未来函数）、E012 = 循环引用、E013 = 依赖列不可用、E015 = 预热不足、E016 = 常量表达式。错误响应统一结构 {"code","message","position":{"offset","line"},"detail"}。

用户因子生命周期与存储【设计】：data/user_data/custom_factors/*.json，id 形如 uf_my_rev（^uf_[a-z0-9_]{1,40}$），字段含 id/version/label/formula/direction/description/created_at/updated_at；草稿（编辑器内试算，不落盘）→ 保存（编译通过 + 试算有非空输出才可保存，fail-closed）→ 引用 → 版本化（公式变更 version+1，旧结果按 version 键隔离）→ 删除（有引用时列出引用方并二次确认）。单个文件加载失败只禁用该因子并提示，不影响启动。

#9 · 模拟盘：账务模型、撮合规则与回测对齐

它在解决什么问题

回测是重放历史，模拟盘是实时向前：它验证的不是「这条曲线多好看」，而是「我现在敢不敢按这个信号操作」。要做到这一点，模拟盘的账务必须像财务报表一样可重放、可审计，且口径必须与回测一致 —— 否则两边的收益数字一对比，全是假差异。

状态要先说清：paper-trading-plan.md 顶部标注「设计稿（未实现）」，描述的是目标形态与实现路径。但本机镜像里 /paper 页面与 /api/paper/* 端点确实存在（86 个只读端点冒烟中「模拟盘」组 12/12 HTTP 200，含 accounts / overview / positions / orders / trades / rounds / nav / stats / compare / auto_rules + 执行绑定）。准确说法是：页面与接口在，本机「下单 → 成交 → 结算 → 净值」的完整闭环从未端到端跑过，总手册 §6.3 明确把它列在「没测过」里。因此本节 上游设计口径 与 本机冒烟现状 必须分开读。

9.1 目标与非目标

  • 目标：把「策略 → 信号 → 决策 → 收益」打通为实时闭环：用虚拟资金跟单自己的策略 / 信号，以真实行情价格模拟成交，每天看到虚拟净值曲线与回合统计。与回测互补：回测重放历史，模拟盘实时向前、无未来函数。
  • 非目标：不接入券商、不做实盘下单、不提供任何资金通道；不做高频 / tick 级撮合模拟（分钟 / 快照级足够）；V1 不做多账户并行（数据结构预留，UI 只开放单账户）。
  • 明确不做：实盘通道、融资融券、期权期货、tick 级盘口撮合、龙虎榜游资席位跟单（可作 V3 规则信号源之一）。

9.2 核心概念与账务模型

概念说明
Account 账户初始虚拟资金 + 费用参数 + 状态（active/frozen/closed）
Order 订单买 / 卖意向；来源 manual / auto（规则触发）；含订单类型与时效
Fill 成交订单的一次实际成交（价格、数量、费用）；append-only 台账

NAV 净值cash + Σ(qty × 市价)；收盘后用日线收盘价定版，盘中用实时价估算

账务正确性原则（镜像财务报表口径）：成交台账是唯一事实源，持仓与净值全部可由台账重放推导；任何修复动作以「冲正成交」记录，不允许直接改持仓文件。这是模拟盘数字可信的地基。

9.6 边界、并发与风控

  • 写并发：域模块内全局写锁；盘中 evaluate 与手动下单竞争同一把锁。
  • 单账户限制：持仓标的数上限（默认 50）防误操作；单笔金额上限（默认不超过可用现金，不提供杠杆）。
  • 冻结：账户 frozen 后拒绝新订单、持仓只读；保留数据可重建。
  • 数据缺失：缺行情 / 缺因子一律留痕 warning + 顺延，绝不臆造成交价（金融数据错误原则）。

10.2 迭代闭环：冷启动 + 每轮九步

冷启动(只做一次): 想法 → 生成 v1 → 基线回测 → 建台账(写入门槛,封存留出集)
每轮: ① 读台账 → ② 提假设 → ③ 改动 → ④ 扫描初筛 → ⑤ 回测 + 分年
      → 拟接受才触发 → ⑥ 终审(敏感性 / 样本外 / 蒙卡) → ⑦ 判定 → ⑧ 记账 → ⑨ 停止检查

两阶段：先粗调，后精调

  • 粗调期（约 v1~v4）：每轮允许一个「改动主题」，可以是一组相关的结构修改（如「给入场加市场环境过滤」）；
  • 精调期（v5 起）：严格执行单变量，一轮只改一处；
  • 切换标志：连续一轮结构改动不再带来大幅改善，即进入精调。

分层验证：常规轮轻，终审重：常规轮只跑「扫描初筛 + 核心回测 + 分年」；终审只在判定为「拟接受」时触发：参数敏感性 + 滚动样本外 + 蒙卡回撤；被回退的轮次不必烧终审。
