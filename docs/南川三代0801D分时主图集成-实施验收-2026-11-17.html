8.1 显示慢 · 根因与修复

项内容
根因（实测）旧脚本每 1.5s 轮询一次 /api/kline/minute?symbol=…&live=true。实测该接口单次耗时 1.9s / 16.5s / 27.9s（三次真实请求），叠加起来覆盖层要几十秒才出现；每次回调还重建 canvas。
修复① DOM 检测 900ms，只查容器不取数；② 数据改为不带 live=true（实测 1.6~2.0s），首次取一次，盘中每 45s 刷新一次，非交易时段有缓存后不再刷新；③ 数据签名（日期+根数+末根时间+末根收盘价）未变就不重算不重绘；④ 覆盖层容器复用，仅丢失时重建；⑤ 绘制走 requestAnimationFrame，并加 ResizeObserver；⑥ 用 textContent 替代 innerText 避免强制重排。
端到端实测已端到端实测 Chrome CDP 9337，打开 002474 详情→分时，轮询等待覆盖层：fetches=1, lastFetchMs=4374；此后 +7s / +14s 两次复查 fetches 仍为 1，draws=2 不再增长，cacheHits=9/16，lastError=""，JS 异常 0。修复前同样 14s 内会重复取数并产生 66 次重绘。
调试入口浏览器控制台 window.__TSP_NANCHUAN_DEBUG：fetches / draws / cacheHits / lastFetchMs / lastError，便于你自己核对「有没有反复取数」。

8.2 信号与通达信不一致 · 根因与修复

项内容
现象你的通达信原图：洋红买线 5.28（约 10:35 起）、绿色卖线 5.38（约 11:00 起）、低位再买线约 5.21（尾盘）。我们旧版：卖！5.400@11:10、买！5.260@14:09、再卖 5.380@11:03——价位与时点都对不上。
排查过程先修掉 num(true)=0 布尔 bug（信号全灭，14:0x 已修）；再排除「补 09:30 竞价根能改变 a10」假设（补与不补，a10@09:48 都是 0.0279、a13 首个仍是 14:08，假设证伪）；最后逐条对照 TRV:=MAX(MAX(H-L,ABS(REF(C,1)-H)),ABS(REF(C,1)-L)) 在分时走势图里的语义。
真正根因通达信「分时走势图」每一根只有一个价格点，公式里的 H/L 退化为当前价（等价于 H=MAX(C,REF(C,1))、L=MIN(C,REF(C,1))），所以 TRV = |C − REF(C,1)|。旧版误用分钟 K 线的真实 H/L，把 ATR 阈值放大约 2~4 倍（实测 09:49 K线口径 0.0279 vs 分时口径 0.0207；10:51 0.0136 vs 0.0079），导致 a12/a13 首次偏离晚几十到几百分钟，锚定价随之失真。这是翻译语境问题，不是改公式口径。
修复后实测已端到端实测 同一真实数据（002474.SZ，230+ 根）：卖！5.380@11:03、买！5.280@10:37、再卖 5.320@09:33、再买 5.210@14:36；与通达信原图 5.38@~11:00 / 5.28@~10:35 / 5.21@尾盘一致。锚定价 a19=C[信号前一根] 复核通过，信号后 5 根保持不变。
顺带修掉的视觉瑕疵本机数据源首根是 09:30 快照柱（volume=0），旧版 a9[0]=0 会从 0 跳到 5.29，画面上出现一条竖直黄虚线。新版在零量根上沿用上一有效均价，并把 9:30 锚点从「首根」改为优先认真实 TIME=93000 根。a9 max step 从 5.2910 降到 0.0210，截图竖线消失。
怎么看：刷新 TSP → 打开 002474 榕基软件 → 点「分时」。画面上绿粗线约 5.38、洋红粗线约 5.28、洋红细线约 5.21，黄色均价虚线平滑无竖线。截图见 /tmp/nanchuan_final.png。
