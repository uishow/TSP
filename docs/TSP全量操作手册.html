Q：「七星175 到底怎么用？」—— 一句话版

它是 ETF 日线轮动策略，收盘后跑，T 日出信号、T+1 开盘成交，持仓 1 只；TSP 只能做模拟盘，不会替你真实下单。

最短路径：更新本机通达信 vipdoc → 跑盘后管道 → 策略页切到「ETF」→ 运行 → 看 rows → 回测页选 ETF 验证 → 验证页调参 → 监控页/模拟盘跟单 → 人工在券商执行。每步的「点哪里、调什么、结果在哪、坑在哪」见 §1。

1 · 七星175 策略完整使用 SOP

先记住这 4 条，能避开 80% 的坑

  1. 它是 ETF 策略：META.asset_types=["etf"]。TSP 几乎所有请求模型默认 asset_type="stock"，不显式指定 ETF 就会报 strategy ... does not support asset_type 'stock'，或静默读错矩阵。
  2. 筛选页默认停在「股票」（前端 useState("stock") 写死）。本机股票策略数为 0，所以不切到 ETF 你会看到一个空的策略库 —— 这就是「茫然」的最大来源。
  3. 收盘后才出票。盘中 9:25~15:00 没有当日 ETF 收盘价，策略按设计不会给结果。11-06 total=0 不是坏了，是 regime=weak / score=11 的双弱风控空仓。
  4. TSP 没有实盘交易接口。/paper 是虚拟账户。真实买卖要人工在券商下单，或把策略接回原聚宽/QMT 版本。

每天出票（盘后）

  1. 先备数据：本机通达信 vipdoc 更新到当日收盘 → POST /api/pipeline/run 返回 job_id → 轮询 GET /api/pipeline/jobs/{job_id} 到 succeeded。本机 18:27 那次实测 145 秒成功，日志会自动把 ETF 分区收敛回 52 只策略池。
  2. 核对数据：GET /api/data/status 看 etf_enriched.latest_date 是否为当日、symbols_covered=52。刚跑完可能短暂 stats_pending=true，等几十秒再看，不是故障。
  3. UI 出票：/screener → 切「ETF」 → 勾选策略 → 「运行」→ 看结果表 total / rows。
  4. API 出票（推荐，参数不会被 UI 默认值坑）：
POST /api/strategies/run
{"strategy_id":"custom_qx175_etf_rotation",
 "as_of":"2026-11-06",        # 注意是 as_of，不是 date
 "asset_type":"etf",          # 必须显式
 "timeframe":"1d"}

# 批量入口（自由 dict，不是 Pydantic 模型）
POST /api/screener/run_all
{"asset_type":"etf","as_of":"2026-11-06",
 "strategy_ids":["custom_qx175_etf_rotation"]}
接口字段坑：/api/strategies/run 用的是 RunRequest，字段是 strategy_id 单数 + as_of；写成 strategy_ids / date 会 422 Field required: strategy_id（本轮亲自踩过）。

结果怎么读：返回 {"as_of","strategy_id","rows","total","elapsed_ms","scores","entry_signal_hits","exit_signal_hits"}。rows 是命中标的（含 OHLC、MA、score），total=1 表示今天该买 1 只，total=0 表示空仓。exit_signal_hits 现在是 51/52（口径收敛前是 1695 条噪音）。

近期实测：10-30 → 501018.SH；11-03 → 159981.SZ；11-05、11-06 → total=0。11-06 市场环境 state=weak, score=11, up_ratio=0.1596，属于设计内避险空仓，不是接口故障。

模拟盘跟单 & 「买卖」到底是什么

  1. /paper → 创建虚拟账户（初始资金、佣金/印花税/滑点）。本机已有 1 个账户、0 订单。
  2. 「绑定策略跟单」→ 选日线策略 / 使用最近完成的回测结果 → 预览并核对参数 → 确认启用跟单 → 可暂停/恢复/重绑快照。
  3. 「自动规则」设 order_type=next_open、仓位模式（固定金额 / 权益%）、冷却天数、最大持仓。时序必须是 T 日收盘信号 → T+1 开盘成交，与回测的 matching=open_t+1 一致，不要 T 日盘中追。
  4. 看结果：订单 /api/paper/orders、成交 /trades、回合 /rounds、净值 /nav、统计 /stats、多账户对比 /compare；数据落 data-local/paper/accounts/{account_id}/。
关键认知：TSP 没有券商下单接口，/paper 是纯虚拟撮合。结算行情按 asset_type 分表读（ETF 读 kline_etf_daily）。真实买卖只能：人工在券商按信号下单，或把这份聚宽/QMT 原策略接回 QMT 实盘。策略源文件本身来自「七星超级175聚宽v3.141-qmt」——那是可接实盘的版本，TSP 这份是移植的研究/验证版本，不要混淆。

4 · 因子怎么弄（这是你问的重点）

一句话：TSP 的「因子」是运行期计算出来的列，不是一张存好的表。你写公式 → 系统编译成 Polars 表达式 → 校验 → 试算 IC → 保存定义（.json）→ 之后在筛选条件、策略评分、因子检验里按名字引用。

4.1 三档写法，从易到难

档写法入口适用
T1 推荐DSL 公式，如 rank(ts_delta(close, 5))/factors?tab=create 公式编辑器绝大多数因子
T2表达式级 Python，AST 白名单（禁 import/def/lambda、禁 map_*/apply/read_*/scan_*），结果必须是单个 pl.Exprlang="python"DSL 表达不了的复杂表达式
T3自由 Python 策略源码 matrix_nativedata-local/strategies/custom/*.py七星175 这种完整策略

DSL 算子（app/factors/dsl.py）：ts_mean / ts_std / ts_sum / ts_max / ts_min / ts_delay / ts_delta / ts_rank / ts_zscore / ts_corr / ts_cov / ts_quantile / decay_linear / rank / zscore / winsorize / power / clamp / if_else / min / max / log / abs / sign / sqrt；基础列见 BASE_COLUMNS；错误码 E001–E016，含窗口纪律检查。

4.2 五步走（含本机实测结果）

  1. 写公式 → POST /api/factors/validate（不落盘）
{"formula":"rank(ts_delta(close,5))","lang":"dsl"}
→ {"ok":true,"errors":[],"dependencies":["close"],
   "referenced_factors":[],"warmup_bars":6,"cross_sectional":true}
  1. 试算 → POST /api/factors/trial（不落盘，近 20~40 日截面 Rank IC）。本机实测 0.1 秒返回 ok=true, n_dates=20, null_ratio=0.1145, ic_mean=-0.0479, ic_std=0.2449, ir=-0.195, ic_win_rate=0.35, t_newey_west=-1.024，每天约 5479 只标的。
  2. 保存 → POST /api/factors/custom（label + formula），或 /api/factors/composite（2~8 个成员 + 权重，带环检测）。门禁是 fail-closed：先编译校验 → 再用最近 40 个交易日试算非空 → 才注册落盘。定义文件在 data-local/user_data/custom_factors/，id 必须 uf_ / cf_ 前缀。
  3. 生命周期：draft → active → watch → retired（POST /api/factors/custom/{id}/status）；改公式会 version+1 且退回 draft。
  4. 检验 / 使用：/factors?tab=library 点「单因子检验」（分组数、权重、调仓频率、佣金、分层净值、IC 均值/胜率、保存候选、加入信号条件）；后端 POST /api/backtest/factor/run / /factor/batch；可用列查 GET /api/backtest/factor/columns。

本机因子库现状：股票 77 个、ETF 70 个；自定义因子目录为空（都还是内置 + 扩展维表派生的）。

因子相关的两个已知限制
  • CustomFactorCreateRequest 没有 asset_type 字段，保存门禁固定用股票面板试算（app/api/factors.py:258,269）。所以「ETF 专用因子」无法在 ETF 面板上通过保存校验。/api/factors/trial 倒是可以显式传 asset_type=etf。
  • 因子值不落盘；回测矩阵只读 enriched parquet 的 14 个存储列，扩展列按设计不落盘（app/factors/ext_factors.py:348）。

4.3 扩展维表 / ext_columns 怎么挂进来

这是「把外部概念、行业、财务字段变成可筛选列」的机制，本机有 12 张维表，主口径是 fuyao_ths_concept / fuyao_ths_industry（同花顺官方离线导入，manifest 完整：概念 390 板块/70601 行/5580 股，行业 320 板块/10287 行/5578 股）。

  • 注册：POST /api/ext-data（id/label/mode=snapshot|timeseries/fields）→ data-local/ext_data/{id}/config.json；写数据用 /upload（CSV/Excel）、/ingest（JSON）、/pull/run（定时拉取）、/backfill（历史回补）。
  • 列名规则：数值字段注册为因子 ext_{config_id}_{field}；字符串字段只进信号条件通道（contains/==/!=），不能当因子；bool 不参与。
  • 投影格式：config_id.field[@HH:MM[:SS]]，逗号分隔；@ 用于多盘表取「该时刻或之前最近一盘」，非法时刻整条丢弃。输出列名为 config_id__field（双下划线）。
  • 支持投影的接口：/api/screener/run、/run_preset、/run_all、/cached、/cached-result/{id}、/limit-ladder、/watchlist/enriched、/kline/daily、/alerts。投影只追加到返回副本，不写回策略结果缓存，避免不同列组合互相污染。
  • PIT 约束：timeseries 按 (symbol,date) 对齐；snapshot 只在单日帧注入、多日历史帧跳过，专门防未来函数。

偏好 monitor_ext_fields 当前指向 fuyao_ths_concept.所属概念 与 fuyao_ths_industry.所属同花顺行业，用于告警富化。
