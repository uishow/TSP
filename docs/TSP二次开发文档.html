1 · 二开分级与选择

1.1 上游的分级（上游说明）

secondary-development.md §2 按升级风险从低到高给出三级：

级别实现方式适用场景升级风险
L1配置、策略文件、扩展数据已有契约能够完成需求最低
L2前端插槽、路由注册；后端策略接口、注册替换新页面、局部 UI、可替换业务规则较低
L3直接修改核心源码核心流程本身必须变化，现有扩展点无法表达最高

上游的选择原则原文要点：

  1. 先确认现有功能能否复用，禁止平行实现第二套数据、策略、缓存或请求逻辑。
  2. 只在存在真实二开需求的位置增加扩展点，不为未来可能出现的需求预埋通用框架。
  3. 插槽或接口无法表达核心行为变化时，可以修改源码；必须缩小改动范围并补回归测试。
  4. 不为了避开一次冲突复制完整页面、服务或引擎。复制会把一次显式冲突变成长期的隐式分叉。

1.2 本机实际多出的第四条路径：运行时 patch（本机已实测）

本机是 digest 固定 + 只读挂载上游镜像 的部署，upstream/ 只是复制出来的参考代码、不覆盖容器上游（README.local.md:41）。因此本机在 L1–L3 之外，实际大量使用 第 4 条路径 P：不改镜像、不改上游源码，用 overrides/ 里的运行时 monkey patch，在 app.main 导入前后替换函数/类方法/模块常量。这是本文 §11 的主题，也是本文档与其它二开文档最大的差异。
路径落点是否要重建/重打镜像升级是否被覆盖本机证据
L1 配置/策略/扩展数据data-local/strategies/、user_data/、ext_data/否否（data/ 不随镜像覆盖）README.local.md:35-45

1.3 决策顺序（本机版）

  1. 需求能否用配置、策略文件、扩展数据表表达？能 → L1。
  2. 是否是新增页面 / 局部 UI / 可替换的小业务规则？上游已有对应插槽或基类且本机镜像里真实存在 → L2。
  3. 是否是本机特有的问题（本地数据源口径、盘后管道、ETF 池、稀疏实时快照、板块单一口径），且上游扩展点无法表达 → P 运行时 patch，按 §11.5 的规范新增。
  4. 核心流程本身必须变化、且本机 patch 会缠绕大量私有状态 → L3，改动最小并补回归，同时接受每次升级手工合并。
  5. 无论选哪条，先读 AGENTS.md、CONTRIBUTING.md、secondary-development.md，检查 git status 保留工作区已有修改（上游 §6 工作流）。
本机补充：MEMORY.md 要求本机交付必须给实测证据并按三态标注。选择 P 路径时，「patch 已装载」不算业务验证（上游 §7 原文：「不得把『扩展已加载』当作业务验证」），必须断言真实数据行数、SSE 终态、出票结果或分区未被截断。

2 · 前端扩展规范

本节依据 secondary-development.md §3 与 page-sdk.md。整体 上游说明；本机未对前端 bundle 做扩展开发，凡「当前开放」清单按上游原文照录，请勿把示例占位名当成已开放插槽。

2.1 何时使用插槽 / 何时使用路由

插槽适合在既有页面增加局部内容：操作按钮或工具栏命令、筛选条件或表单字段、表格列和详情面板、个股/策略详情附加标签页、设置页独立配置区。新增完整页面应使用路由与导航注册，不要把整页塞进某个插槽；改变核心页面数据流、状态模型或主要布局时应直接改核心代码并按 L3 管理。

3.4 继承与组合的边界

继承只用于表达稳定的「是一种策略实现」关系。需要同时组合过滤、评分、通知等能力时，分别注册多个小实现，不创建拥有大量可选方法的万能基类。优先组合的场景：一个服务需要多个独立规则；行为需按资产类型或运行上下文选择；扩展只需装饰默认结果而非完全替换算法；依赖缓存、仓库或通知服务，需通过明确构造参数注入。

与本机 P 路径的关系 本机已实测：本机 14 个 patch 里，只有 source_policy 的 install_app_policy() 用「替换模块级函数」、board_taxonomy 用「替换模块常量」、其余多为「包装类方法 / 包装函数」。它们都遵守 §3.3 的 fail-closed 与「不暴露 app.state」精神，但不是在 app.extensions 注册表里注册，而是由 bootstrap.py 统一装配，见 §11。

能力声明的粒度（重要）

datasets 声明是数据集级的，不是资产类型级的：声明了 realtime，整个全市场实时轮询周期（含指数与 ETF 部分）就全部路由给插件。若快照只覆盖 A 股股票：指数行情自动降级为日线推导值（非实时）、不报错；ETF 实时计数为 0。这是当前框架的设计行为——要么在数据里尽量覆盖指数/ETF，要么接受降级并在 description 里说明覆盖范围。

get_minute 的 datetime 时区契约

  • datetime 必须是北京时间墙钟（naive，如 2026-08-28 09:35:00），与日K 的 date 语义对齐；不要返回 UTC 或带时区的时间。前端分时图按交易时段时轴（09:30–11:30 / 13:00–15:00）映射，UTC 口径的帧会导致全部点位落在时轴外、分时图空白。
  • amount 单位为元；无法提供可靠分钟成交额时返回 null，不得伪造。成交额缺失后前端停止绘制后续均价线并显示「—」。
  • 入口守卫 kline_sync._enforce_minute_beijing_wallclock 对所有分钟源强制归一：带时区 → 自动换算北京墙钟；naive 但整体呈 UTC 特征（如 01:30）→ 自动 +8 纠偏并记日志；完全无法识别的口径 → 拒收并回退 TickFlow。契约仍要求源头写对，守卫只是兜底。
  • 可选类属性 minute_history_days = 5 声明 1 分钟历史深度（交易日）；未声明视为深历史。浅源声明后个股分时档位自动收窄并默认 5 日，深源默认 20 日。
  • full_minute 契约：声明 full_minute 并把 full_minute_data_provider 路由到该源即接入「全量分钟」；必须实现 get_intraday_batch（或已有 get_minute 自动回退），可选 get_intraday_latest（未实现时服务降级为仅修复轮，节奏下限抬到 60s）。两个方法都必须返回原始价（不复权）：本地分钟库以 raw 基准落盘（.raw_basis），返回已复权价格会与本地存储混基准，产生静默错误价格。

4.4 路由机制（仅参考）

后端启动时 loader.py 扫描 plugins/：读每个子目录的 plugin.yaml → hidden: true 跳过；否则调 check 检测可用性 → 可用则动态 import entry 指向的 Provider 类并注册进 _PROVIDERS → 不可用则记录状态、设置页显示但不可切换。注册后，插件和用户 YAML 自定义源走完全相同的路由路径（provider_has_dataset / get_provider），无需额外集成代码。

本机约束 本机已实测：本机 TSP_SOURCE_POLICY=1 下，overrides/source_policy.py::install_app_policy() 会把 custom_loader._register_one_plugin 包装成「只允许 local_quant」、把 custom.get_provider 对其它名字直接 denied()，并从 _PROVIDERS / _PLUGIN_STATUS 里弹出所有非 local_quant 的源。因此本机不能按上游方式直接新增第三方数据源插件；本机唯一的行情来源是只读挂载的 plugins/local_quant/ + 宿主机桥接。想改数据口径，请走 bridge/ 或 overrides/（§11），不要改 plugin.yaml 期待它生效。

5.3 字段契约（必填 / 可选）

数据集必填内部字段可选 / 备注
dailysymbol（如 000001.SZ）、date（交易日）、open/high/low/close（不复权 OHLC）、volume、amount—
adj_factorsymbol、trade_date（除权日期）、ex_factor（复权因子）明细列 dividend / bonus / allot / allot_price / prev_close，提供即落库、缺省为空，供等差显示投影与全精度因子链重建
realtimesymbol、last_price、prev_close、open/high/low、volume建议额外提供 amount、change_pct、change_amount、amplitude、turnover_rate、name；缺失时部分字段由 pipeline 回算，精度取决于可用输入
depth5symbol、asks（卖五档，嵌套数组 [[价,量], ...]，卖一→卖五）、bids（买五档，买一→买五）每档取前两个元素按数值解析为 [价格, 手数]，无法解析的档位跳过；数量沿用「手」，前端算封单额时再乘 100
financialsymbol（唯一硬性要求，缺 symbol 的帧被丢弃）、period_end（报告期 YYYY-MM-DD，缺此列不参与报告期合并）、announce_date（公告日期，缺省时按报告期排序）一个配置覆盖五张表；每表 canonical 列见下

realtime 的 pct_unit（单位必须显式声明）

change_pct / amplitude / turnover_rate 统一小数制（0.0366 = 3.66%）。百分制单位必须在 realtime 数据集上显式声明，不做数值猜测——0.05 既可能是 0.05% 也可能是 5%，数值无法区分。

datasets:
  realtime:
    url: https://api.example.com/snapshot
    pct_unit: percent   # 接口返回 3.66 表示 3.66%; 小数制源声明 decimal 或省略
声明行为
pct_unit: percentchange_pct / amplitude / turnover_rate 无条件 /100
pct_unit: decimal三列原样透传
未声明change_pct 按截面中位数归一（A 股涨跌停 30% 上限使两种单位物理可分）；amplitude / turnover_rate 置 None 交由 pipeline 按价格与股本口径重算，并记录 WARNING
列已配置 transforms视为用户已接管该列单位，原样透传

financial 的 canonical 列与单位陷阱

  • 请求自动注入 table 参数：metrics / income / balance_sheet / cash_flow / shares；shares 表额外注入 latest（当期 True / 全历史 False）。
  • 映射为「外部字段 → 内部列」一对一：同一外部字段名只能映射到一个内部列；两张表存在同名字段且含义不同时无法分别映射，需要上游区分字段名或只映射其一。两个外部字段映射同一内部列会在保存时被校验拒绝。
  • 某批响应里完全缺失（而非为 null）的字段，该批不落该列，跨批/跨轮合并会自动补 null。
  • metrics 核心指标：eps_basic / eps_diluted / bps / ocfps / roe / roe_diluted / roa / gross_margin / net_margin / debt_to_asset_ratio / revenue_yoy / net_income_yoy / operating_cash_to_revenue / inventory_turnover。百分比列存「百分点」（12.3 表示 12.3%），与 realtime 的小数制不同。
  • income / balance_sheet / cash_flow 金额单位均为元；shares 的 total_shares / float_shares 单位为股。历史换手率按公告日（缺则报告期）取有效股本，无 float_shares 时回退维表最新股本。
  • 报告期合并按 (symbol, period_end) 逐列取最新非空值：多源字段可并集共存互不覆盖；但切换生效源后不再拉取的表不会自动清空，旧数据保留到被新数据覆盖。

5.8 用 AI 生成映射配置

操作步骤：拿 API 文档（接口地址 / 请求方式 / 返回字段说明）→ 试拉一次拿到返回 JSON 示例 → 把 Prompt 模板 + 文档 + 示例一起发给 AI → 把生成的 YAML 贴到 data/data_sources/xxx.yaml → 设置页「重新加载」→「试拉测试」验证。上游提供的 Prompt 模板要点（custom-data-source.md §「用 AI 生成映射配置」）：

  1. 输出标准 YAML，包含 name / display_name / auth / datasets。
  2. 每个数据集的 field_map 把接口字段名映射到内部字段名。
  3. 日期类字段若格式不是 YYYY-MM-DD，加 transforms 里的 parse_date。
  4. 只配置能提供的接口，不存在的数据集不要写。
  5. 附「内部字段对照表」：daily 的 symbol/date/OHLC/volume/amount；adj_factor 的 symbol/trade_date/ex_factor；realtime 的 last_price/prev_close/OHLC/volume/amount/change_pct/change_amount/amplitude/turnover_rate；minute 的 datetime 必须是北京时间墙钟（如 2026-08-28 09:35:00），不要返回 UTC。
  6. 明确告知：上游若返回百分数值（3.66 表示 3.66%），在 realtime 声明 pct_unit: percent，不要依赖数值自动识别；逐列转换也可用 transforms: turnover_rate: "value / 100"。
本机不适用 本机已实测：本机 source_policy.py::install_app_policy() 把 custom.create_provider / custom_loader.create_provider 整体替换为 denied()，并把所有 provider 偏好字段强制钳制回 local_quant（coerce_preferences / validate_preferences）。因此纯 HTTP YAML 自定义源在本机不会被创建或注册；data/data_sources/*.yaml 在本机部署里不是有效扩展入口。上述契约仍完整保留，供阅读上游、在 Dev 模式或未来放开策略时使用，不要写成「本机已接入 mock_source」。

7 · 扩展包结构 / 安装 · 更新 · 回退 · 卸载 / 生效与失败隔离

依据 extension-packages.md 与 external-data-source-packages.md。统一入口是「设置 → 导入与备份」（/settings?tab=import）：策略、因子、信号页的小盒子，以及数据源的「安装插件」都会进入同一页面。

7.1 导入识别规则

  • 策略 .py、信号/因子 .json 和资源 ZIP 可混合多选；复用原有依赖闭包、冲突比较、批次回滚和缓存刷新。

  • 根目录有 plugin.yaml 的数据源包走 Provider 安装契约；安装后在「已安装扩展」配置 Key、验证并选择数据能力，不会自动切换行情来源。
  • .js/.mjs 页面产物、单个 .tsx 或本项目已有源码页面走 Page Pack SDK（§6）；确认信任和同名替换，通过浏览器加载校验后刷新生效。
  • 根目录有 extension.yaml 的 ZIP 使用后端扩展契约，可同时包含配套前端页面；安装仅暂存，重启主程序后生效。

7.3 安装 / 更新 / 回退 / 卸载

动作行为生效时点
安装上传 ZIP → 静态预检（名称/作者/版本/能力/兼容）→ 确认信任 → 写入 data/extensions/<id>/versions/<version>/ 并原子写 state.json后端包需重启主程序；页面产物刷新浏览器

取消待生效更新详情区支持 cancel-update即时

7.4 生效与失败隔离（上游说明）

  • 限 20 MiB 压缩包、80 MiB 解压总量、1000 条目；拒绝越界路径、重复/大小写冲突、符号链接、原生库、wheel 和安装脚本；不写入程序源码目录。
  • 启动时验证文件摘要、兼容性、ID、接口命名空间和注册冲突，再运行启动钩子；成功后才发布路由、通知格式化器和配套页面。新后台失败时保留原版本，新页面不会先切换；单个扩展错误不阻断主程序或其他扩展。
  • 启停、回退、更新和卸载在下一次主程序启动时应用；浏览器刷新不能替代后台重启。旧页面可能保留在已打开标签中，重启完成后需刷新浏览器同步。
  • 失败隔离覆盖已提交的路由、策略注册与安装状态；可信代码自行产生的文件、网络等副作用无法自动撤销。扩展与主程序同权限，不是沙箱。
  • 管理使用面板登录会话，不向开放 API Token 授权；无密码时仅接受本机同源管理。首版面向单进程部署；多 worker 应全部停止后统一维护和重启，不提供跨 worker 在线切换。

8.2 Token 体系（上游说明（V1 已实现））

  • 存储沿用 secrets 模式：data/user_data/tokens.json（chmod 0600）：{id, name, token_hash, scopes, created_at, last_used_at, revoked}；明文 Token 只在创建响应中出现一次（前缀 tsp_ + 32 字节随机 hex）。
  • 认证通道与现有单密码并行不替代：本机/内网 UI 登录照旧；Authorization: Bearer tsp_... 是外部调用方专用第二通道。
  • 中间件顺序：访问密码门 → Token 识别（有 Bearer 头则走 Token 路径，免密码会话）→ scope 校验 → 限流。
  • Token 泄漏 = 面板数据泄漏：默认只读 scope、可随时吊销、创建时明文只显一次；paper:trade 永不默认。

8.4 限流与 CORS

  • 按 Token 滑动窗口：默认 120 req/min；触发 429 + Retry-After。重活端点（回测/挖掘提交）另受既有 heavy_job_limiter 并发约束。

  • 响应头：X-RateLimit-Remaining / X-RateLimit-Limit。
  • Token 限流只作用于 Bearer 路径；UI 会话不受 Token 桶约束（避免误伤本机 UI）。

11.3.3 spawn worker 不继承主进程内存 patch → config 必须在主进程注入

这是本机最容易复发的一类问题（手册 §7-6、§8-P7）。稳健优化 /api/backtest/optimize-robust/stream 与 walk-forward /walkforward/stream 的 Query 参数上游根本没有 asset_type，_opt_backtest_kwargs() 也不返回它，于是 worker 里 StrategyBacktestConfig.asset_type 落到默认 "stock"，报 ValueError: strategy ... does not support asset_type 'stock'; supported=['etf']。

更关键：and first.asset_type 会一路传给 resolver.resolve / build_matrix_cache_profile / load_market_data_matrix_for_backtest，所以只放宽 validate_context 校验是不够的——那样会去读 kline_daily_enriched（股票）而不是 kline_etf_enriched，结果全错。必须让 config 本身就是 asset_type="etf"。

而 worker 使用 mp.get_context("spawn")，子进程不继承主进程的内存 patch。因此 overrides/optimize_asset_fix.py 只在主进程构造优化 config 时把 asset_type 写进 backtest_kwargs，随 config 一起序列化传给 worker；worker 侧无需任何 patch。同理 matrix_range_hint.py 必须挂两个点：主进程 BacktestEngine.load_market_data_matrix_for_backtest，以及主进程接收 worker 异常的 app.backtest.worker.run_worker_task（这里还能拿到 task 里的完整请求区间）。

推论：任何「只在主进程内存里改了函数/类」的 patch，对 spawn 子进程里的调用都无效；要么像 optimize_asset_fix 一样把状态序列化进 config，要么像 matrix_range_hint 一样在主进程边界改写结果，要么靠 sitecustomize.py 在每个 worker 解释器里重装（见下）。

11.3.4 sitecustomize 的 fail-closed

# overrides/sitecustomize.py（13 行，PYTHONPATH=/app/overrides 使其被自动加载）
import os
if os.environ.get('TSP_SOURCE_POLICY') == '1':
    try:
        from overrides.source_policy import install_network_guard, install_app_policy
        install_network_guard()
        install_app_policy()
    except BaseException:
        # Python 通常会吞掉 sitecustomize 的错误；策略失败必须在任何应用/厂商代码
        # 执行前终止解释器。
        import sys
        sys.stderr.write('SOURCE_POLICY_INITIALIZATION_FAILED; refusing to start\n')
        os._exit(78)
  • Python 默认会吞掉 sitecustomize 里的异常，若不显式 os._exit(78)，零外联策略可能在「看起来启动成功」的状态下失效——这是典型的 fail-open 风险，因此用 BaseException 兜住并硬退出。
  • 它保证 container 内每一个 Python worker 解释器（包括 spawn 出来的）在导入任何应用代码前都装好网络守卫与 app policy，弥补 §11.3.3 的内存 patch 不继承问题。
  • 环境踩坑 本机已实测（MEMORY.md「环境踩坑」）：容器内任何普通 python -c 都会被它强制装载零外联策略，install_app_policy() 在裸进程里失败即 os._exit(78)（SOURCE_POLICY_INITIALIZATION_FAILED; refusing to start）。纯源码核查请用 python -S（跳过 site/sitecustomize），或把核查脚本放到宿主机对 /tmp/tsp_v0331/app 快照执行（§12）。

11.5 新增 patch 的规范（幂等 / best-effort / 可观测 / 不阻断启动）

归纳本机 14 个模块的共同写法，新增 overrides/<name>.py 必须满足：

  1. 幂等标记：用模块属性或类属性防重复包装，例如 if getattr(_mod, "_tsp_xxx_installed", False): return，装完置 True。启动或偏好保存可能被多次触发（见 #13 的迁移函数两处调用），重复包装会层层嵌套。
  2. best-effort 异常：所有可选逻辑用 try/except Exception（个别用 BaseException 仅限 sitecustomize）包住，只 log.warning(...) 并返回原结果；绝不因为补丁自己失败而拖垮启动、偏好保存或盘后管道。原文措辞：「任何异常只记 WARNING 并返回原结果」「异常回退原方法」「收敛是 best-effort：任何异常只记 WARNING，不影响管道本身的结果」。
  3. 日志可观测：装载成功打一行带稳定前缀的 logger.warning("XXX: installed")（本机用 WARNING 级确保容器日志里一定可见），运行时关键分支打可检索的证据行，如 SPARSE_FLUSH_GUARD、ETF_CONVERGE、MONITOR_STRATEGY_FIX、PIPELINE_ETF_ADJ_TOLERATED。排查时 docker compose logs app --since 30m | grep -Ei '...' 能直接定位。
  4. 不阻断启动：不改上游文件、不写程序目录、不动已有 parquet；只替换函数/类方法/模块常量。装载顺序按 §11.3 的「模块级引用 → 之前；类方法/模块常量 → 之后」判定，并在 bootstrap.py 写注释说明为什么放这里。
  5. 状态序列化：若目标调用可能在 spawn worker 里发生（§11.3.3），必须把修正写进可序列化的 config/task，或在主进程接收结果处改写，不要依赖内存 patch 传递。
  6. 金融语义不放宽：只替换错误文案、降级已知不可用、修正资产口径，不裁剪回测区间、不自动回退掩盖异常、不伪造缺失数据、不补零（见 #10、#11、#14）。
  7. 附带回滚点：数据侧修复同时备份受影响分区 / 规则 / 偏好到 data-local/integrity_backups/，并在回滚说明里写明「移除哪一行 install 才不会自动再修正」。

11.6 与上游「安装包升级保护」的关系

上游 secondary-development.md §8.1 说明：桌面安装包与 Docker 镜像发布携带 app/upgrade_manifest.json，后端每次启动扫描程序目录，把用户「修改/新增」的程序文件常备备份到 data/upgrade_guard/live/；版本变化时生成对比报告（可恢复 / 需手工合并 / 已一致 / 新增文件可恢复），在「设置 → 系统设置 → 升级保护」展示。守卫不自动合并代码；源码运行（无清单）时功能自动停用。

本机为什么不吃这套：本机把定制放在 overrides/ 只读挂载卷里，而不是镜像的程序目录 /app/app。因此升级保护扫描的是上游程序目录（本机没改过，无冲突可报），overrides/ 则完全在它的视野之外——这既是优势（升级不覆盖），也意味着补丁的目标符号可能随上游升级变化而失效，必须用 §12 的 AST 核对来补上这一层。

本机 14 个 patch 里，绝大多数是 运行时替换函数 / 包装类方法 / 替换模块常量。它们对上游的依赖不是「文件内容相同」，而是「目标符号仍然存在且签名一致」。上游可能重构函数体、调整 import 形式、改方法参数顺序，而 git diff 显示「无冲突」——但 KlineRepository.get_enriched_latest_asset 少了一个参数，install_enriched_integrity() 里的包装就会在运行时报 TypeError。
