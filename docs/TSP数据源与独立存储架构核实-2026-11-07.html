TSP 数据源与独立存储架构 · 核实报告

问题：TSP 数据是独立存放的吗？为什么不能链接到本地数据源？ · 2026-11-07

一、结论（先说）

① TSP 数据确实独立存放：规范化后落在 data-local/（parquet 列存 + DuckDB 视图），是从数据源"拷贝+规范化"出的快照，不直接读 TDX 原始文件。

② TSP 不但能连本地数据源、而且本来就在连：bridge/tdx_local.py 是只读适配器，直接读通达信 vipdoc/*.day 二进制日线。所以"连不上"是误解；回测只看到 2025-11-04 起，是因为灌进 TSP 的那份快照起点被设成了 2025-11-04，并非 bridge 读不到老数据。

二、数据链路（架构）

通达信 TDX
vipdoc/*.day（二进制，1994~今）
→
bridge/tdx_local.py
只读适配器：解析 .day / 前复权导出 / gpcw
→
data-local/
kline_daily 等 parquet + DuckDB 规范化快照
→
回测/分析引擎
polars_expr，读 DuckDB 视图

关键点：引擎只读最右的规范化快照，不每次回测都现场解析 TDX 二进制；bridge 是 TDX 与 TSP 之间的"翻译+搬运"边界（也是容器跨越宿主机读 Mac 上 CrossOver TDX 的通道，走 host.docker.internal:7818）。

三、铁证（已端到端实测）

1
运行时数据目录独立：容器挂载 data-local → /app/data；回测读的是这里面的 kline_daily 分区，与 TDX 原始 vipdoc 是两份不同文件。
2
bridge 确实连本地 TDX：tdx_local.py 顶部 TDX_ROOT=/Users/.../CrossOver/Bottles/通达信/.../tdx-new，直接 open(vipdoc/market/lday/xxx.day,'rb') 逐条解析 32 字节记录。
3
本地 TDX 日线长达几十年：sh/lday 6053 个、sz/lday 5928 个 .day 文件；抽样 sh600866.day 首条记录 = 1994-08-18（约 30 年）。bridge 完全能读到。
4
快照起点是被"设"出来的，不是能力限制：scripts/repair_start_boundary.py 中 partition=.../kline_daily/date=2025-11-04 且 start=datetime(2025,11,4)，报告字段 historical_import_not_live_capture:True——说明股票日线历史导入只是"设了起点边界"，并非实时抓取老数据。

四、为什么 TSP 用独立快照，而非"直接链接"TDX

原因说明
格式/规范化TDX 是二进制 .day（32 字节、价格×100/1000）、独立的前复权导出 .txt、财务 gpcw 压缩包；TSP 需要统一的 canonical 前复权 schema + 列存 parquet，无法直接用二进制做分析。
性能回测一次载入 130 万+ 行；每次现场解析 TDX 二进制极慢，预规范化的 parquet + DuckDB 列存查询快得多。
可复现 / 隔离快照带 reproducibility_sha256，回测结果可复现；若直接连实时 TDX，市场一更新结果就漂移，无法取证。
容器化边界TSP 跑在 Docker（Linux/arm64），TDX 是 Mac 上 CrossOver 的 Windows 程序；容器无法直接读宿主机 TDX 文件，必须经 bridge 服务（7818 端口）跨边界——bridge 就是"链接"本身。
数据源解耦引擎只认规范化快照，数据源可替换（TDX / akshare 等），互不绑架。

五、对你"回测只能 2025-11-04 起"的根因与出路

根因：kline_daily 快照的起点被 repair_start_boundary.py 设为 2025-11-04（单次边界修复，historical_import_not_live_capture），后续盘后管道只往前追加，从不回填更早历史。所以无论你选 2024 还是 2010，引擎都夹到 2025-11-04。
出路（要 2024 起长回测）：用 bridge 已具备的读取能力，按更长区间做一次性历史导入写进 kline_daily。脚本已现成：scripts/repair_start_boundary.py 里的 sync_and_persist_daily_batch(symbols, repo, …, start_date=…, end_date=…) 就是入口，把 start 从 2025-11-04 改成你想要的起点（如 2024-01-01）即可回填，再 run_pipeline() 重建 enriched 与 DuckDB 视图。此操作会改写行情分区，建议单独排期 + 先备份。
