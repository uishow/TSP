2026-11-10 14:55–15:10 · TSP v0.3.34 · 容器 tsp-local · 主站 127.0.0.1:3018

用户原话：「1、docker内存调回降到 20GiB。2、Key 放在本机 runtime/fuyao.env 这个方法，如果下次 TSP 升级，会不会生效呢？3、我点击策略页，会显示『策略加载失败…』」

结论速览（三句话）

  1. 回测上限已从 36GiB 降到 20GiB（按你选的「只降回测上限」，Docker 内存保持 23.71GiB、没重启、零中断）。安全关系恢复了：20 < 23.71。
  2. 升级后 fuyao Key 会继续生效，不用重填。因为它压根不在容器里、也不在镜像里；升级换的是镜像，碰不到宿主机的那个文件。升级后只要做 3 步核对（见 §2）。
  3. 策略页报错已修好：一个 AI 写的策略同时放了两种「入口」，上游只准一种；删掉多余那个、把它的两条基础过滤搬进保留的那个，重载后 load_errors=0，7 个策略全部加载。

三态：三项的接口、真实数据、语义都跑过了 已端到端实测；升级真的发生时会怎样属于未来推演，只能给「按挂载与验收脚本核对」的硬证据 仅静态核对（现有 v0.3.34 环境里没法真的升一次级）。真实浏览器画面仍请你 Cmd+R 确认 未验证。

① 回测上限：36GiB → 20GiB（Docker 内存没动）

你选了「只降回测上限」。我按这个执行：没有改 Docker 桌面版的内存、没有重启 Docker、没有中断任何服务。

项目改之前改之后怎么改的
回测上限（长任务用到多少内存就主动收手）36 GiB20 GiBPUT /api/settings/preferences/backtest-worker-rss-limit 传 {"gib":20}，HTTP 200，免重启、可逆
Docker 内存（整台虚拟机的硬天花板）23.71 GiB23.71 GiB（保持不动）没动 settings-store.json；容器 Up 30 minutes (healthy)，没重启
两者关系36 > 23.71 → 上限比天花板还高，等于没用20 < 23.71 → 恢复安全关系长任务会先被温和收手，而不是整机内存被撑爆后被强杀
要诚实说明的代价：以前实测过的「1658 天全市场回测」峰值约 31.2GiB，现在会在 20GiB 处被主动收手，这条长历史全市场回测跑不完了。这不是坏了，是拿「能跑完」换「不会把整个 Docker 撑崩」。日常用法不受影响：限定股票池（例如 300 只，约 2.88GiB / 17 秒）照常；verify_tsp.py 的常规数据链路本轮仍全通过。
结果在哪看：打开主站 /api/settings/preferences，找 backtest_worker_rss_limit_gib，应该是 20。

出错怎么查：回测任务直接报「内存到上限」而不是整站卡死，就是新上限在起作用，属正常；若整站无响应，先 docker ps 看容器是否 healthy。

② 下次 TSP 升级，这个 Key 还会生效吗？—— 会，不用重填

一句话理由：Key 从头到尾就没进过容器、也没进过镜像。升级换的是「镜像」这一个文件，动不到你 Mac 上 runtime/fuyao.env 这个普通文件。所以升级不会让它失效。
东西放在哪换镜像会不会被替换 / 删掉实测证据
Keyruntime/fuyao.env（本机，权限 600）不会。docker inspect 的 5 个挂载里没有 runtime/；容器里 env | grep FUYAO_API_KEY = 0 条、也没有这个文件已端到端实测
数据快照（龙虎榜 / 竞价名单）data-local/fuyao/recap/（10 个 JSON）不会。这是「宿主机目录直接映射」，不是 Docker 数据卷；换镜像不删，docker compose down -v 也只删具名卷、删不到它已端到端实测
只读补丁 + 启动装载overrides/fuyao_recap.py + bootstrap.py 末尾 7 行不会。overrides/ 是只读挂载卷，镜像里没有这些文件，换镜像不会覆盖已端到端实测
被替换的只有镜像里的 /app/app、/app/static会换 —— 这正是需要「补丁核对项」的原因，见下仅静态核对

还有一层保险：升级验收脚本 scripts/doctor.py 里有一条硬性规定 —— 「谁把 runtime/ 挂进容器，直接判 FAIL」（check_compose() 第 98–99 行）。也就是说，只要以后升级改了 compose，验收会自动替你盯住「Key 不能被带进容器」这条边界。本轮体检这条是 [PASS] compose_invariants: ... no runtime mount。

升级后必做的 3 步（不做的话是「数据变旧」，不是「失效」）

第 1 步 · 看补丁还在不在
docker logs --tail 200 tsp-local | grep FUYAO_RECAP
看到 FUYAO_RECAP_ACTIVE ... ready=True = 正常。看到 FUYAO_RECAP_PATCH_SKIPPED = 新版上游把接口改了，补丁安全退回（主功能照常，只是这两个页面回到「未配置」），这时按新签名改一下 overrides/ 里的挂载卷文件即可，不要去改镜像。看到 NO_SNAPSHOT = 该跑第 2 步了。
第 2 步 · 刷新一次数据（升级这个动作本身不会刷新数据）
.venv/bin/python scripts/fuyao_recap_sync.py --days 5
不用重启容器，容器每次读的都是文件。这一步只是让快照日期跟上，Key 不用重填。
第 3 步 · 刷新浏览器 + 跑一次验收
Cmd+R 看「异动监控」和「复盘页」；再跑 docker exec -i tsp-local /app/.venv/bin/python - < scripts/verify_tsp.py，确认 fuyao.aicubes.cn 仍被拦、主数据源仍是 local_quant。

哪些情况会让页面回到「未配置」

  • 新版上游改了接口：custom.is_custom_provider / get_provider 签名变了，或不再带 FuyaoError → 记 SKIPPED 安全退回，不白屏、不阻断启动。
  • 新版上游改了复盘页端点或返回字段 → 数据可能对不上，需要重新核对一次契约（也不崩）。
  • 升级时手工清空了 data-local/ → 快照没了，但 Key 还在，重跑一次同步脚本就全回来。
  • 忘了跑第 2 步 → 数据停在旧日期（过期，不是失效）。
要补进升级 SOP 的一条（本轮发现）：现有升级回滚包 backups/upgrade_v0.3.34_20261109_1249/ 只备份了 compose.yaml / doctor.py / .env / overrides/ / 偏好 / 当日四张行情分区，没有单独备份 data-local/fuyao/recap/（那个包是 11-09 做的，早于本次接入）。虽然换镜像本来不会删它，但建议以后升级前加一行备份，防误操作：
cp -r data-local/fuyao/recap backups/upgrade_<版本>_<日期>/fuyao_recap/
Key 文件不用备份进回滚包：它本来就不随升级变化，多复制一份反而多一处泄密点。

③ 策略页「加载失败」：一个文件多写了一个入口

大白话根因：AI 生成策略时有两种写法。一种写「当天的判断」（叫 filter），一种写「要看前几天走势的判断」（叫 filter_history）。这个「强势反包」策略要看前一天，所以它声明了「我要用第二种」，但代码里两种都写了。上游规定「声明用第二种，就只能有第二种」，于是整份策略加载失败、策略页顶部弹红字。

核查 / 动作结果三态
复现用户报错GET /api/strategies 的 load_errors 恰好 1 条：{"file":"/app/data/strategies/ai/ai_3c551f13.py","error":"python_history_legacy strategy must declare only filter_history"}已端到端实测
上游规则出处镜像内 app/strategy/engine.py:612：elif filter_history_fn is None or filter_fn is not None: raise ValueError(...)仅静态核对
扫全部 4 个 AI 策略只有 ai_3c551f13.py 一个坏了；ai_780a199d.py 同为「看历史」类型但只写了 filter_history，正好是合规范本；另两个是「当天判断」类型，只有一个 filter，都合规已端到端实测
修法先备份到 runtime/ai_3c551f13.py.bak.20261110_1455.py；删掉多余的 filter()，把它那两条基础过滤（close>0、volume>0）等价搬进 filter_history() 的判定条件里并加 fill_null(False)；其余选股逻辑、参数、评分一字未动已端到端实测
语义验证合成 3 天「前日阴线 −3% → 今日放量阳线反包」数据，命中 1 行（11-06）；把今日成交量改成 0（模拟停牌）后命中 0 行，证明搬过去的基础过滤确实生效已端到端实测
页面验证POST /api/strategies/reload → {"ok":true,"count":4}；再查 /api/strategies → load_errors=0；?include_research=true → 7 个策略全部加载，ai_3c551f13 在列（backend=python_history_legacy）已端到端实测
两个容易误判的点：① /api/strategies 默认只列「已发布」策略，AI 草稿标记了 research_only=true，所以默认列表里看不到它 不是没修好，要加 ?include_research=true 才看草稿区。② 改完文件不会立刻生效，引擎有缓存，必须调一次 POST /api/strategies/reload（不用重启容器）。另外上游启动时会把「一直加载失败的内置残留策略」自动归档，好在这次修完 load_errors=0，下次重启也不会被移走。
会复发，先说清楚：上游的 AI 生成器在「生成时校验」这一步有个缺口 —— 它对「当天判断」和「分钟策略」都查了「不能多写入口」，唯独没查「看历史」这一种（ai_generator.py:: _strategy_entrypoint_error 最后只问「有没有 filter 或 filter_history 任一个」）。所以以后再让 AI 生成「要看前几天走势」的策略，还可能写出同样两份入口、策略页再报同样的红字。
镜像里的文件不能改（铁律）。可选的一劳永逸做法：在 overrides/ 加一个很小的运行时补丁，在「生成/保存策略」时检查这一条并让 AI 重写，带一键开关、升级后自动退回。你没要求，我没有擅自加，列在 §6 未完成清单里等你拍板。

⑤ 升级兼容与回滚

  • 本轮没碰：镜像 / tag / digest / compose.yaml / upstream/ / 容器内 /app/app / /app/static / 主数据源 / 任何行情口径 / 二开补丁代码。override 计数仍是 21。
  • 改的三样都可逆：① 运行时偏好（一条 PUT 改回 36）；② 一个 AI 草稿策略文件（原样备份在 runtime/ai_3c551f13.py.bak.20261110_1455.py，拷回即可）；③ 文档。
  • 策略文件为什么不进 Git：.gitignore 里 data-local/* 把运行数据（行情 / 回测 / fuyao / 任务状态）一律排除，AI 生成的策略草稿属于用户数据，不是二开代码。所以这次修复只在本机；如果以后重建 data-local/，这个修复会丢，需要照 §3 再做一次（或把该文件加白名单，等你定）。
  • 升级后最坏情况：新版上游改了接口 → 补丁记 FUYAO_RECAP_PATCH_SKIPPED 原样退回，TSP 主功能照常，最多两个页面回到「未配置」；绝不白屏、绝不阻断启动。回测上限是偏好值，升级不影响；策略文件在挂载卷，升级不覆盖。

回滚命令

  1. 回测上限改回 36GiB：见 §1 那条 PUT 命令。
  2. 策略文件还原：cp runtime/ai_3c551f13.py.bak.20261110_1455.py data-local/strategies/ai/ai_3c551f13.py，再 POST /api/strategies/reload。
  3. fuyao 旁路整体关闭：TSP_FUYAO_RECAP=0 重启，或删 bootstrap.py 末尾 7 行（详见 docs/竞价异动与龙虎榜-fuyao特色数据接入验收-2026-11-10.html §7）。
