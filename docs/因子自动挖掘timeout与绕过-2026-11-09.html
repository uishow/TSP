1. 一句话结论

timeout 不是你操作错：它是「前端默认 30 秒」与「服务端同步预筛 40~53.6 秒」的不匹配，纯前端上限。 用脚本直接调同款 API 即可绕过（tools/mining_bypass.py 已实测跑通提交+轮询）。

但本部署自动挖掘当前还被两道真实数据缺口卡住，与 timeout 无关： ① 7 个财务因子恒失败：根因是二开补丁未覆盖回测读取路径（非上游），详见《财务因子7个修复清单-二开层方案》； ② regime 市场环境表仅 245 天，导致任何长窗挖掘 run 都因缺前一交易日环境而失败。 两者都需你拍板是否修数据源 / 补算，不在「点同步按钮」能解决的范围。

2. 现象：自动挖报到 timeout

网页「因子 → 自动挖掘」按钮点击后，浏览器约 30 秒弹出 Error("timeout")，挖掘没有结果。

点哪里：因子页 → 自动挖掘 → 设置资产类型/区间/预算档 → 启动。 结果在哪看：正常应出现候选因子与 IC/IR；现在只看到 timeout。

3. 根因（两层）

前端层（直接原因）

TSP 前端对 /api/backtest/mining/auto 这个 POST 用了默认 30 秒超时（前端常量 Pf=3e4）， 且调用处未单独传 timeoutMs。

服务端层（触发条件）

该接口在同一个请求内同步做因子 IC/IR 预筛（auto_screening）。实测：

  • 全历史窗口（6505 交易日）预筛 53.6 秒；
  • 短窗（2025-01-01 起，约 460 交易日）预筛仍 40.5 秒。

浏览器在 30 秒处主动断开 → 抛出 timeout。另有一次服务端因「盘后数据管道在排队期间改了数据」而 failed （mining data generation changed after the run was queued），属另一类失败。

结论：30 秒是纯前端上限。绕过方法 = 不用浏览器按钮，改由脚本直接调 API（脚本没有 30 秒上限）。

4. 因子模块是干什么的

TSP 内置 77 个因子（动量 / 均线偏离 / 趋势 / 波动率 / 量价 / 流动性 / 价格位置 / 收益形态 / 超买超卖 / 规模 / 财务）。 「自动挖掘」= 量化研究 / 选股因子挖掘机：先在历史区间对 77 个因子算 IC（预测力）、IR（稳定度）、t 值 → 用质量门槛 gate（|IC|≥0.02、|IR|≥0.15、|t|≥1.5、max_q=0.2）筛掉弱预测/不稳定/计算失败的因子 → 把通过的组合成多因子候选策略 → 你满意后可 promote/publish 推到回测验证。它不直接下单。

5. 数据页财务同步：入口与状态

入口：网页「财务 / Financials」页的同步按钮 → 后端 POST /api/financials/sync/{table} （table = all / metrics / income / balance_sheet / cash_flow / shares）。 状态查 GET /api/financials/status。

现场状态（2026-11-09 16:40 实测）：

available: true metrics 43917 行 / 5490 只 last_sync 2026-11-09 07:54 syncing: false
关键纠正（2026-11-09 二次复核，结论已变更）：我此前说「先同步财务数据就能消除 7 个财务因子失败」是错的；同步后这 7 个因子依然 ic=null。但更早的「须改上游 financial_sync」判断也错了——实测复核后定位到根因在本项目二开层： ① 本表 announce_date 100% 为空，因子加载会过滤掉 announce_date 为空的行 → 快照恒为空集 → 返回 None（7 因子全 null）； ② 6 个比率列（roe/毛利率/净利率/营收增速/净利增速/资产负债率）在 metrics 表根本不存在； ③ 但算这些比率要用的「原材料」在 income/balance_sheet 表覆盖率 99.6%（revenue/net_income/总资产/净资产/总负债 缺失率均 <0.4%）。 真相：我们已有二开补丁 overrides/financials_metrics_enrich.py 会算这些比率，但它只接到了网页读取线（get_financial_df），没接到回测读取线（load_fundamental_snapshot）；且回测直接读原始 parquet、绕过补丁。修复 = 把换算也接到回测读取线 + 派生 announce_date，完全在二开层内、不碰上游。详见《财务因子7个修复清单-二开层方案-2026-11-09.html》。

6. 两个真实限制（实测）

限制一：7 个财务因子恒失败（根因 = 二开读取路径缺口，可修复）

因子加载读 /app/data/financials/metrics/part.parquet，要求该表含 7 个列（bps, roe, gross_margin, net_margin, revenue_yoy, net_income_yoy, debt_to_asset_ratio）且 announce_date 非空。实测： announce_date 100% 为空（loader 把所有行过滤成空集 → 快照 None），6 个比率列全部缺失。但算这些比率的原材料在 income/balance_sheet 表覆盖率达 99.6%。 结论：无需改上游。既有二开补丁 overrides/financials_metrics_enrich.py 已能算这 6 个比率，只是没接到回测读取线；把换算也接到 load_fundamental_snapshot + 派生 announce_date 即可（约 25 行、二开层内）。详见《财务因子7个修复清单-二开层方案-2026-11-09.html》。

限制二（已解决，2026-11-09）：regime 市场环境表原仅 245 天

挖掘 regime_alignment 需要「前一交易日市场环境」（/app/data/regime_history/part.parquet）。 该表原仅 245 天（2025-11-04 ~ 2026-11-06），远短于 enriched 的 6505 天 → 任何跨 2025-11-04 前的长窗挖掘都 failed。 2026-11-09 已用 regime_builder.run_regime_batch 对全历史补算，现覆盖 6505 天（2000-01-04 ~ 2026-11-09）（原子写、已端到端验证）。 长窗挖掘通道已打通：实测 2020-01-01~2026-11-06 长窗 run 55c2838b/edc63587 均 succeeded_with_budget_exhausted（error=null）。

财务缺口（限制一）根因已定位为二开读取路径缺口，修复方案见《财务因子7个修复清单-二开层方案-2026-11-09.html》（待实施）；regime 缺口已于 2026-11-09 补算完成（原子写、已验证，无需再处理）。

7. 绕过脚本 tools/mining_bypass.py

绕过前端 30 秒上限的脚本（已在仓库 tools/，仅标准库）。两种模式：

模式 A：--mode auto（等价于网页按钮，无超时）

python3 tools/mining_bypass.py --mode auto \
  --start 2025-01-01 --end 2026-11-09 --budget exploratory

完全复刻按钮逻辑（先 L1 预筛再启动），但没有 30 秒上限，会等预筛完、拿 run_id、轮询到结束。

模式 B：--mode runs（真正异步、零阻塞）

python3 tools/mining_bypass.py --mode runs \
  --factors momentum_20d,ma20_bias,rsi_14,macd_hist,volatility_20d,turnover_rate \
  --start 2023-01-01 --end 2026-11-06 --budget exploratory

POST /api/backtest/mining/runs 立即返回 run_id、完全异步（不做 53.6 秒预筛，需自填 factor_names； 因子 ID 从 GET /api/factors 取，共 77 个）。随后脚本轮询 /runs/{run_id} 到终态。

注意：窗口需 ≥~460 交易日通过可用性校验。regime 原仅 245 天会卡住长窗；2026-11-09 已补算至 6505 天后， 实测 2020-01-01~2026-11-06 长窗 + 8 个非财务因子提交 runs，run 55c2838b/edc63587 均 succeeded_with_budget_exhausted（error=null）—— 证明长窗挖掘通道已彻底打通（此前该长窗会 failed，见第 6 / 10 节）。

9. 能否盈利（诚实边界）

因子挖掘给的是历史样本证据（IC/IR + 回测收益），不能直接保证盈利。A 股现实里有：交易成本/滑点、过拟合、前视偏差、 行业轮动阶段性失效。本部署还叠加：ETF 未前复权、策略池静态、财务维度 7 个因子缺失（二开读取路径缺口，可修复，见《财务因子7个修复清单-2026-11-09》）、regime 数据已于 2026-11-09 补算至 6505 天（已解决）。

把它当「研究假设生成器」：挖出的候选必须再过严格样本外（OOS）/ walk-forward 验证，再小额实盘试跑， 稳定后才谈得上「可能盈利」。把回测收益当业绩承诺是危险的。

11. 操作指引（点哪里 → 发生什么 → 结果在哪看 → 出错怎么查）

想绕过 timeout 跑自动挖掘

  1. 点哪里：不用网页按钮；在终端跑 tools/mining_bypass.py --mode auto（或 --mode runs 自填因子）。
  2. 发生什么：脚本直接调同款后端 API，无 30 秒上限，预筛完拿 run_id 后轮询。
  3. 结果在哪看：脚本末尾打印 status / 预筛耗时 / 达标数 / 候选数；候选也可在网页因子结果页看。
  4. 出错怎么查：若报 市场环境数据覆盖不完整 → 见新-3（regime 缺口）；若 7 个财务因子失败（ic=null）→ 见新-2（二开读取路径缺口，方案见《财务因子7个修复清单-2026-11-09》）；若 EnrichedGenerationUnavailable → 等盘后数据更新完再跑。

想看财务数据是否已同步

  1. 点哪里：网页「财务」页，或接口 GET /api/financials/status。
  2. 结果在哪看：available:true + last_sync 时间。
  3. 出错怎么查：即便 available:true，因子仍可能失败（列缺口），属源覆盖问题，非同步动作问题。
