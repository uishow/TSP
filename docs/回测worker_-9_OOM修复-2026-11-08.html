三、根因诊断链（为什么是 -9）

#环节证据与推理
1页面走的是另一条路径页面用 GET /api/backtest/strategy/stream（SSE + spawn 独立 worker）；之前 13:38 的验收用的是 POST /api/backtest/strategy/run 且带 80 只 symbols。两条路径不是一回事，所以「之前验证通过」不代表页面能跑
2请求不带 symbols日志里的完整 query 没有 symbols，上游按全市场 5510 只加载。这是内存暴涨的入口
3长历史放大了数据量11-07~11-08 回填后 kline_daily 从 245 个交易日变成 6504 个（16,487,647 行）。即便回测只用 2024 起，加载/预热阶段的全市场矩阵也远大于回填前
4worker 峰值 15.92 GiB修复后成功那次的 stats.worker.peak_rss_bytes 给出定量值。旧容器 MemTotal=9.67 GiB，主进程常驻约 2.3~3.1 GiB，worker 可用不足 6.5 GiB → Linux cgroup OOM Killer 直接 SIGKILL，父进程收不到任何 result，报 backtest worker exited without result (exitcode=-9)（app/backtest/worker.py:450）
5软限制形同虚设preferences.json 里 backtest_worker_rss_limit_gib=16，而容器硬上限只有 9.67 GiB。软限制设得比硬上限还大，永远来不及触发，所以没有出现「内存超过上限，已中止」的友好中文提示，直接是 -9
6范围保护没开config.py:125 backtest_range_guard=False，虽然 BACKTEST_MAX_SERVER_DAYS=186，但 2024-01-01~2026-11-07 共 1042 天没有被拦截，任务照常启动再被杀
7之前调的 16G 丢了~/Library/Group Containers/group.com.docker/settings-store.json 实测 MemoryMiB=10204（≈9.97 GiB），对应 Linux VM 9.665 GiB。GUI 设置在 Docker Desktop 重启/更新后未保持，这就是「调过又回落」的原因
不是这些原因：不是数据损坏（DuckDB 直查行数/范围完好）、不是 SSE 端点坏了（带 symbols 正常 done）、不是策略报错（error=None）、不是 asset_type 设错（日志里是 stock）。纯粹是内存容量不足。

四、修复动作（可追溯）

  1. 备份：把 settings-store.json 复制为 backups/docker-settings-store_20261108_1957.json（585 B，含原始 MemoryMiB=10204）。
  2. 停 Docker Desktop：docker desktop stop。必须先停，否则运行中的 Docker Desktop 退出时可能用旧值覆盖配置；compose.yaml 有 restart: unless-stopped，容器会自动回来。
  3. 改配置：MemoryMiB: 10204 → 20480（20 GiB）。宿主物理内存 48 GiB，占用合理。
  4. 启 Docker Desktop：docker desktop start，等引擎就绪（实测 13 秒服务恢复 /health 200）。
  5. 验证 + 复跑：确认 MemTotal=19.50 GiB、配置未被覆盖、四表与 DuckDB 行数完好，再原样复现全市场 2024 起 SSE 回测两次。
# 精确命令（顺序不能颠倒）
CFG="$HOME/Library/Group Containers/group.com.docker/settings-store.json"
cp "$CFG" backups/docker-settings-store_20261108_1957.json
docker desktop stop
# 编辑 settings-store.json： "MemoryMiB": 10204  ->  "MemoryMiB": 20480
docker desktop start

七、边界与剩余风险

  1. 余量偏小：worker 峰值 15.92 GiB + 主进程约 2.3 GiB ≈ 18.2 GiB，容器 19.50 GiB，余量约 1.3 GiB。当前场景实测通过，但不建议同时开多个全市场回测。
  2. 更长区间大概率仍会 OOM：本次是 688 个交易日。若改成 2000 起全历史（6504 个交易日，约 9.5 倍），worker 峰值会远超 20 GiB。未验证。要跑请：① 把 MemoryMiB 调到 28672（28 GiB，宿主 48 GiB 仍够）并按第四节重启；或 ② 限制 symbols / 缩短区间。
  3. 软限制仍是 16 GiB：backtest_worker_rss_limit_gib=16，现在与 20 GiB 硬上限搭配合理（worker 15.92 GiB 刚好没触发）。若将来把容器调更大，别把软限制调到超过硬上限，否则又会退化成含糊的 -9。
  4. 范围保护关闭：backtest_range_guard=False，超长区间不会被提前拦截，只会启动后 OOM。如需更早给出中文提示，可在设置页开启（本轮没有改这个配置）。
  5. 策略收益 -88.4% 只是验证样本：本轮目的是证明「不报 -9」，不是评价策略；全市场、单区间、固定参数、含基础筛选，不能当真实业绩。
  6. GUI 设置可能再次回落：Docker Desktop 更新或重置可能把 MemoryMiB 改回默认。建议每次 Docker Desktop 大版本更新后按第 ② 步自查一次。
