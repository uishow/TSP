2到底卡在哪（本轮实测 / 源码核对）

查到的事实证据
网页通用请求默认等 30 秒前端 index-CAVr8Awa.js：const Pf=3e4, bt=3e5（30 秒 / 300 秒两个常量）。同一个文件里已有 5 处长请求显式用了 timeoutMs:bt（300 秒）

网页自己也知道要等更久按钮旁文案写着「约 1-3 分钟」，却给了 30 秒上限 —— 属于上游的疏漏，不是我们数据或环境的问题
后端源码确认「只有挑因子是同步的」/app/app/api/mining.py 的 start_auto_run()：先同步跑 screen_all_factors(...)（约 40 秒），拿到达标池后调 manager.start(...) 把任务交给独立 worker；mining_runtime.py 开头写明「只在 spawned worker 里执行」
另一个入口 /runs 是秒回start_run() 不做筛选，校验完直接 manager.start(...) 并返回任务状态；tools/mining_bypass.py 注释也写「立即返回 run_id，完全异步、零阻塞」
一句话：卡住的是「先挑 40 秒因子」这一步，不是挖掘。挖一启动就进后台了。

3好消息：后台机制本来就有（不用我们造）

现成能力状态本轮实测
POST /api/backtest/mining/auto在先筛因子再交后台；约 40 秒同步段
POST /api/backtest/mining/runs在不做筛选、直接交后台、秒回任务号；需要自己给因子名单
GET /api/backtest/mining/runs在拉到 6 条历史任务，全是 succeeded，含创建/开始/结束时间
GET /runs/{id}在返回状态 + 完整请求（因子名单、区间、预算等）
GET /runs/{id}/events在SSE 实拉到 queued → running → progress 事件，含「加载因子面板 / 校验市场环境数据 / 行数 492,180」；支持 Last-Event-ID 断点重连，前端原本就用 EventSource 接它
GET /runs/{id}/result在实拉到完整结果：selected_factor_count=11 / candidate_count=1 / valid_fold_count=11 / skipped_fold_count=1 / elapsed_ms=20,594 / peak_rss=1.49GiB，还有每个因子的 IC、方向、得分
POST /runs/{id}/cancel、候选 promote / publish在取消与「提升 / 发布候选因子」也都有现成接口
原生页面 /mining在本来就有进度条、结果区、历史列表，用的就是上面这些接口
结论：「后台挖 + 前台展示」需要的零件，TSP 一件不缺。我们要做的只是换一个不被 30 秒掐断的入口，然后把这些现成接口接到一个能看进度的页面上。

4三条路线比选

方案 A · 独立新页「挖掘后台」（推荐）

做法：跟「大单监控」完全同一套装法——把 bundle.js + page.json 放进 data-local/ext_pages/mining_bg/，TSP 自动在左侧栏加一项。纯网页代码，不写任何后端、不碰原系统一行。

页面上两个按钮：

按钮背后发生什么用户体验
「精确挖（先筛因子）」网页原生 fetch 调 /auto。浏览器原生请求没有 30 秒上限（30 秒是 TSP 自己封装的放弃计时器，不是浏览器限制）页面显示「正在挑因子，约 40 秒」+ 转圈；拿到任务号后接 SSE 显示进度，完成后显示结果表
「立刻后台挖」调 /runs，因子名单用「上次筛出的 49 个」或从 /api/backtest/factor/columns 取，页面上可勾选秒回任务号，页面立刻显示「已交给后台，可以关网页」；随时回来在历史任务里看

「历史任务」页签：拉 /runs 列出所有任务（包括原网页、脚本启动的），点任一任务看状态、进度事件、结果；可取消、可提升 / 发布候选因子（都是现成接口）。

优点代价 / 边界铁律
零后端改动、零镜像改动、热加载无需重启容器、可一键删目录回滚；原 /mining 页完全不动；关网页不丢任务「精确挖」那 40 秒挑因子期间要留着这个标签页（挑完交后台后就可以关）。这段时间若强制关掉，服务端可能已经启动了任务，可从历史任务找回；不会损坏数据完全符合

方案 B · 运行时补丁，顺手把原按钮也修好（可选加餐）

做法：复用项目已验证的 overrides/multi_asset_patch.py 范式，新增一个小补丁：自动发现 index-*.js，只在内存里把 miningAutoStart 那一处补上 timeoutMs:3e5（300 秒，TSP 自己给其它长任务用的现成时长）。要求全文恰好命中 1 处，否则记 ..._SKIPPED 并原样返回上游文件；一键开关 TSP_MINING_TIMEOUT_PATCH=0。

优点代价 / 边界铁律
原「因子挖掘」页按钮立刻不再报 timeout，进度条、结果页、历史全是原生，不用另开页面；改动极小（一个补丁文件 + 注册一行）用户仍要开着页面等约 40 秒才看到「已提交」，不算「点一下就走」；它改的是原页面行为（虽不改文件）。上游若换了混淆变量名，补丁会 SKIPPED 自动退回 30 秒（定制失效，主功能正常）符合（不落盘、不改镜像、可降级）
为什么用字面量 3e5 而不是变量名 bt：混淆变量名会随版本变，写死数字只依赖一个稳定字符串片段，升级时更容易自动适配；这是从回测多选补丁升级实战里学到的。

方案 C · 后台代提交，真正做到「点一下就走」（最彻底，风险最高）

做法：在 overrides/ 加一个自己的小路由，页面点「精确挖」立刻回「已排队」；我们的路由在服务端后台线程里慢慢跑那 40 秒预筛并替你启动任务，页面轮询自己这个小任务的状态，再接 TSP 的 /runs 看进度。

优点代价 / 边界铁律
连 40 秒都不用等，页面秒回，关网页完全无影响；体验最贴近「后台挖」的字面意思要写 Python 去调上游内部函数 screen_all_factors（有版本契约风险），还要自己做一层任务状态 / 并发 / 失败重试；复杂度和升级适配成本最高符合，但要按 P0 标准做自动发现 + 精确校验 + 缺失即降级

方案 D · 直接改容器内前端文件（否决）

否决。改 /app/static、改镜像 / tag / digest、把带哈希的文件名写死 —— 这些正是「二开不得影响 TSP 升级」铁律明令禁止的。升级会被覆盖或成为阻碍，不做。

5推荐组合与理由

推荐：先做 A；如果你还想要原按钮不报错，再叠加 B。C 先不做。
顺序为什么
① 先 A零风险、当天可用、原系统一行不动（符合你 #105 说过的「原系统的不变，做个新增页出来」），而且已经满足「后台挖 + 前台看」；「历史任务」还能把之前脚本跑过的任务一起收进来看
② 可选 BA 用顺手后，若你仍习惯从原「因子挖掘」页点按钮，再加这个合规补丁，两处都能用；不做也不影响 A
③ C 暂缓A 的 40 秒等待只在「精确挖」点下去那一次，而且页面有明确提示；为省这 40 秒去碰上游内部函数不划算。真觉得碍事再上
为什么不推荐「只做 B」：B 虽然改动最小，但你仍要守着页面等约 40 秒，而且它动的是原页面行为。A 才是真正把「点一下 → 后台跑 → 回头看」这件事完整交给一个你自己可控的新页。

7关掉网页会不会丢

时刻会不会丢
「立刻后台挖」点下去之后不会 任务号已在 TSP 服务端落盘，进度事件也写在服务端，随时能重放
「精确挖」拿到任务号之后不会 同上，页面显示的「已提交」意味着服务端已启动 worker
「精确挖」还在挑因子的那 40 秒里强制关网页不确定 服务端可能已筛完并启动任务，也可能请求中断；不会损坏数据，回新页看一眼「历史任务」即可确认，没有就重新点一次。方案 C 才能把这一段的确定性也补上
任务跑完之后不会 结果存在 /runs/{id}/result，随时可查；本轮实拉的历史任务就是昨天跑完的
