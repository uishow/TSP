0一句话结论

已修复（机制 + 数据双验证）。在本地插件 plugins/local_quant/provider.py 新增增量刷新端点 get_intraday_latest，让 minute_refresh 的 repair_only 从 true 变为 false，刷新间隔从被强制抬到的 60s 下限 恢复为用户设定的 6s。增量端点数据已实测返回每只标的最新 N 根分钟K，落盘走按 symbol 合并去重、不覆盖当日历史。板块盘中滞后的根因已消除；最终延迟数值需在交易时段实测确认（非交易时段 gate_reason=outside_trading_hours、rounds=0 属正常）。

1用户可见症状

你在盘面看到的现象：概念 / 行业 / 板块的盘中涨幅、轮动、分时图，比真实行情慢 31~46 分钟。这些数据来自 kline_minute 当日分区，而该分区由后台守护线程 minute_refresh 持续刷新。刷新越慢 / 越滞后，板块图就越旧。

数据链路：板块涨幅 = market_snapshot(30s SSE) × extDataRows 聚合；板块分时 / 轮动 = 读 kline_minute/date=今天/part.parquet。所以只要 kline_minute 刷新及时，板块图就及时。

2根因定位

minute_refresh 有两种刷新模式：

模式触发条件节奏
增量（increment）自定义源实现 get_intraday_latest用用户设定的间隔（本部署 6s）
全天修复（full / repair）自定义源没有 get_intraday_latest（即 repair_only=true）间隔被抬到 60s 下限，且每轮拉全市场 → 单轮 31~46 分钟
真因：本部署的本地数据源 plugins/local_quant 只有 get_minute / iter_minute / get_intraday_batch，唯独缺 get_intraday_latest。因此 _custom_supports_increment() 返回 False → repair_only=true → 刷新被钉在 60s + 全市场批量，造成 31~46 分钟滞后。iter_minute 是盘后 / 历史同步用的，与盘中刷新互不相交，不是延迟根因（P0 已补，但与本延迟无关）。

实测佐证（非交易时段）：

GET /api/settings/minute-refresh/status
  repair_only : true      ← 根因标志
  interval_seconds : 6    ← 用户设定值，但被 repair_only 抬到 60s
  capability_ok : true    ← 能力门控不是 blocker（local_quant 已声明 full_minute）
  gate_reason  : outside_trading_hours  ← 非交易时段不跑，rounds=0 属正常

3改动内容

仅在本地插件 plugins/local_quant/provider.py 新增一个方法（约 25 行），未碰镜像、未碰 upstream、未碰容器内 /app/app。该文件经 compose.yaml 以 :ro bind-mount 进容器，属于我们自己的二开层。

新增方法（契约见 kline_sync.fetch_intraday_custom_latest）

def get_intraday_latest(self, symbols=None, count=3, asset_type='stock'):
    """稳态增量刷新端点：被 minute_refresh 探测到即解除 repair_only。"""
    if os.environ.get('TSP_LOCAL_QUANT_INTRADAY_LATEST','') in ('0','false','False','.disabled'):
        return self._frame({'rows':[]},'minute')        # 一键关闭 → 退化为修复轮
    if symbols is None:                                  # 缺省自行解析全市场标的池
        try:
            inst = self.get_instruments(asset_type=asset_type)
            symbols = [r['symbol'] for r in inst
                       if isinstance(r,dict) and r.get('symbol')] if isinstance(inst,list) else []
        except Exception:
            symbols = []
    if not symbols:
        return self._frame({'rows':[]},'minute')
    end = datetime.now(); start = end.replace(hour=0,minute=0,second=0,microsecond=0)
    frames = []
    batch = max(1, int(os.environ.get('TSP_LOCAL_QUANT_MINUTE_BATCH','20')))
    for i in range(0, len(symbols), batch):
        result = self._request('minute', symbols=symbols[i:i+batch],
                               start_time=start, end_time=end,
                               asset_type=asset_type, freq='1m', require_latest=True)
        frames.append(self._frame(result,'minute'))
    df = pl.concat(frames, how='diagonal_relaxed') if frames else self._frame({'rows':[]},'minute')
    if not df.is_empty() and count and 'datetime' in df.columns:
        df = df.sort(['symbol','datetime']).group_by('symbol', maintain_order=True).tail(count)  # 只留最新 N 根
    return df
落盘安全：返回的增量帧交给 _write_minute_partition，它先读旧分区 → 只对本次触及的 symbol 合并去重（按 [symbol,datetime] keep last）→ 未触及的 symbol 原样保留。所以增量只 upsert 最新几根，绝不会覆盖当日历史分钟。
优雅降级：若增量取数失败，fetch_intraday_custom_latest 捕获异常返回空帧 → 计为空轮 → 连续空轮后自动退回到全天修复（即升级前行为），不会白屏或阻断启动。

4.3 待交易时段确认

非交易时段 gate_reason=outside_trading_hours，刷新轮不运行（rounds=0 属正常）。最终延迟数值（是否从 31~46 分钟降到可接受范围）需在交易时段实跑确认——届时观察 rounds 递增、healthy=true、板块图与行情同步。

6升级安全性

本改动不影响 TSP 版本升级：

  • 未改镜像 / tag、未动 compose.yaml digest、未动 upstream/、未直写容器内 /app/app 或 /app/static。
  • plugins/local_quant 是本部署自有插件（bind-mount :ro），升级镜像后该文件仍在，方法照常生效；若上游某版本把 get_intraday_latest 纳入官方契约，本方法也不会冲突（同名同契约）。
  • 若上游重构导致 _frame / _request 签名变化，最多是本方法报错 → 优雅降级为空轮 → 退回修复模式，绝不阻断启动。

7残留风险与待办

1. 盘中延迟数值未实测：最终是否从 31~46 分钟降到可接受范围，需在交易时段实跑确认（观察 rounds / healthy / 板块图同步）。本回合在交易时段外，只能验证机制 + 数据。
2. 增量轮仍走全市场标的池：get_intraday_latest(symbols=None) 会解析全市场 ~5500 只标的。若桥接吞吐不足，单轮仍可能偏慢；届时可加「窄窗口」或桥接侧「批量最新」端点进一步优化（不影响当前已生效的 6s 间隔与增量模式）。
3. 与 P0 的关系：P0 补的 iter_minute 是盘后 / 历史同步契约；本回合补的 get_intraday_latest 是盘中增量契约。两者互补，都落在同一个本地插件，互不影响升级。
验收三层对照：接口能返回（repair_only=false 实测）✓；真实数据（增量端点返回最新 N 根分钟K 实测）✓；语义正确（合并去重不覆盖历史、交易日延迟待实测）◐。
