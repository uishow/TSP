一、两个问题各一句话答

Q1：为什么选 2024-01-01，页面却显示「日线数据范围 2023-09-04」？
因为那是「指标预热数据」的加载起点，不是回测起点。上游固定要额外加载约 120 个自然日历史来算 N 日新高 / MA20 / 量比等指标，2024-01-01 往前推 120 天正好是 2023-09-04。真正的收益与交易从 2024-01-02 开始（净值曲线 688 个点），2023 年那几个月不会被算进收益，也不是数据错乱。
Q2：为什么选 2023-01-01 就报 exitcode=-9？
区间从 688 个交易日变成 930 个，全市场 worker 峰值内存从 15.92 GiB 涨到 20.33 GiB，超过当时的 19.50 GiB 容器上限 → 内核 SIGKILL。现已把 Docker 内存调到 27.36 GiB、软件内存上限调到 24 GiB，2023 起回测实测成功（1443 笔交易 / 930 点曲线）。
截图里那块「本次数据范围」为什么是旧的？错误框已写明「本次回测未生成新结果，下方仍展示上一次成功结果」——你看到的 4,113,821 行 · 2023-09-04 ~ 2026-11-06 是 上一次 2024 起成功回测的数据。现在重跑 2023 起成功后，这块会变成 5,317,893 行 · 2022-09-05 ~ 2026-11-06（预热窗口同样往前提 120 天）。

二、Q1 预热窗口详解（有证据链对照）

2.1 源码依据

app/backtest/strategy.py:474 / :1074 / :1241 / :1465
warmup_days = max(120, int(max(profile.warmup_bars, 1) * 1.6))

回测引擎要计算「N 日新高」「20 日均线跌破」「5 日量比」这类指标，第一天必须有之前的数据才能算出来，所以会把输入数据的起点往前推一段。这段只用于预热指标，不产生交易、不计入收益，也正是「不使用未来数据」的正确做法。

2.2 两次成功回测的实测对照

你选的回测起点页面显示的日线数据起点提前天数加载行数净值曲线点数证据链

规律完全固定：无论选哪一年，数据起点都往前约 120 自然日；净值曲线长度始终等于「所选区间内的交易日数」。你截图底部的「2024-01-01 ~ 2026-11-07 · 688 天」也印证了回测区间本身是对的。
怎么区分「数据起点」和「回测起点」：页面「本次数据范围」说的是引擎加载了多少行情（含预热）；底部结果摘要 / 净值曲线 / 交易列表说的是实际回测区间。两者差 120 天属正常，不必修正。

截图里「同期基准 · 366 行 · 2025-05-08 ~ 2026-11-06」是因为本地指数数据只覆盖约一年，不是回测数据缺失。它只影响「基准对比曲线」的长度，不影响策略收益和交易计算。这是已知限制，尚未补齐。

三、Q2 报错根因：两道内存闸门

#环节实测证据
1区间变长DuckDB 直查：2024 起 = 688 个交易日、2023 起 = 930 个交易日、2020 起 = 1658 个交易日
2第一道：容器硬上限复现 2023 起（当时 19.50 GiB）→ 38 秒后 event: error / backtest worker exited without result (exitcode=-9)，容器本身仍 healthy。这是 Linux cgroup OOM Killer 的 SIGKILL
3把容器调到 27.36 GiB 后，第二道闸门暴露再跑 2023 起 → 返回中文提示「回测任务内存超过上限 16.0GiB (当前 16.8GiB), 已中止」；容器日志 backtest worker rss 16.77 GiB exceeds limit 16.00 GiB, terminating。这是 preferences.json 的软件软限制在主动刹车，避免把整机拖死
4真实峰值两道闸门都放开后成功那次：stats.worker.peak_rss_bytes = 21,829,189,632 = 20.33 GiB
所以这次不是「上次没修好」：上次把 9.67 → 19.50 GiB 确实解决了 2024 起；你把起点再往前推一年，数据量与内存需求同步上涨，撞到了新的上限。同时软件软限制 16 GiB 是 11-08 之前设的，比新的容器上限还小，成了第二道误杀点。
两道闸门的正确关系：软件软限制（现 24 GiB）应略小于容器硬上限（现 27.36 GiB），这样超限时先给出中文提示而不是含糊的 -9；同时软限制又要大于任务真实峰值（20.33 GiB），否则会把正常任务误杀。

六、内存梯度与更长区间的边界（重要）

回测起点交易日数worker 峰值内存当前配置（27.36 GiB / 软限 24）
2024-01-0168815.92 GiB（实测）✅ 通过

外推依据：每增加一个交易日约多 0.018 GiB（(20.33−15.92) ÷ (930−688)）。宿主物理内存 48 GiB，即便把 Docker 调到 40 GiB 也会让 macOS 明显吃紧，且软上限要同步调到 36 GiB 左右。

想跑 2020 起 / 2000 起，推荐这样做

  1. 缩小标的池（推荐）：在回测请求里给 symbols 指定一批标的（如 80~500 只），内存按比例下降。实测同一 SSE 端点带 80 只、2024 起只需几秒、336 笔交易。这是不占内存、不用再重启 Docker 的做法。
  2. 分段回测：把长区间拆成几段分别跑，而不是一次跑 6 年全市场。
  3. 再调大内存（不推荐长期用）：MemoryMiB=40960 + 软限 36 GiB，按第四节顺序重启；宿主只剩约 8 GiB 给系统，风险高。
另外：backtest_range_guard=False（config.py:125），超长区间不会被提前拦截，只会启动后 OOM。如需在界面上更早得到提示，可在设置页开启范围保护（本轮没有改这项）。
