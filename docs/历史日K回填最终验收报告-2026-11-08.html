五、页面读数澄清（重要，纠正此前结论）

纠正：11-07 的执行记录里把 rows:0 / stats_pending=true 写成「统计重建暂态，等一会就好」。本轮查了源码，这个说法不准确：rows:0 是上游的恒定设计，不会「等好」。

5.1 为什么会显示 0 行（源码证据）

现象源码位置真实原因
daily.rows=0、enriched.rows=0/app/app/api/data.py:216 / 254 / 472_safe_aggregate_daily() 直接 return {"rows": 0, ...}，注释写着「零数据扫描」「不再查询行数」。为性能故意不扫全表，恒定返回 0
stats_pending=true 常驻/app/app/services/data_status_cache.py:46result["stats_pending"] = busy or bool(due)。只要有缓存项到期（due）或后台同步在跑（busy）就为 true；storage 的 TTL 只有 60 秒（data.py:158），会周期性复发
日期范围却是对的data.py:205~216earliest_date / latest_date / trading_days 是遍历 date=* 分区目录名算出来的，不查数据行，所以准确实时：2000-01-04 ~ 2026-11-06 / 6504
结论：连续 3 次请求 stats_pending 都是 true，但容器日志没有任何 data status refresh failed，pipeline jobs 最近 5 条也无卡在 running 的。这是缓存标记，不影响回测——第四节已用真实回测证明数据可用。

六、2026-11-08 两次故障与修复（可追溯）

6.1 全量回填完成，容器却陷入重启循环

项内容
症状310 个月全部回填完成后，容器 Restarts 从 2 → 3 → 5 → 15，/health HTTP 000；日志每次停在 startup phase start: DuckDB view kline_daily；一次全表 count(distinct symbol,date) 查询直接 exit 137
根因上游 _persist_daily_chunks 按月把结果写成多个 part-stream-N.parquet，长历史累积出 398,514 个小文件 / 6481 个分区。启动时 DuckDB 视图 glob 要展开约 40 万个文件的 schema，内存与耗时爆炸；叠加 Docker 内存只有 9.67 GiB
解法停容器 → 新建 scripts/compact_kline_daily_partitions.py 把每个分区合并成单个 part.parquet → 重启服务
证据[done] 完成 6479 分区 / 删除 398470 个小文件 / 用时 253s；最终 6504 个 part.parquet、0 个 part-stream；/health 200、healthy
合并脚本的安全设计：先写 part.parquet.tmp（不匹配业务 *.parquet glob）→ 校验合并前后行数一致 → os.replace 原子改名 → 才删除旧小文件。已有 part.parquet 时直接删旧文件，可随时中断续跑。

6.2 compact 首次灰度失败：ArrowTypeError

Unable to merge: Field date has incompatible types: date32[day] vs dictionary<values=string>。原因：pq.read_table(p) 会沿 Hive date=* 目录做 dataset 扫描，把整个 kline_daily 都纳入，误读别处不同类型文件。解法：改成 pq.ParquetFile(str(p)).read() 逐文件读。逐文件扫描确认样本分区的 part-stream 全是 date32[day]。

6.3 补 2025-11-03 后又冒出 111 个小文件

--force 补单日仍走流式写入。解法：再跑一次 compact。核验 rows=5424、date32[day]。教训：任何用回填脚本写过数据之后，都必须再跑一次 compact。

6.4 全量指标重算 OOM（Killed）

项内容
症状sync_adj_factor added=50767 成功后，run_pipeline() 在 pipeline.py:291 join_asof 阶段被 Killed（SIGKILL / OOM），主服务仍 healthy
根因上游 _RAM_LARGE_BYTES = 8 GiB 把 9.67 GiB 容器误判为「内存充裕」，不收缩批次；enriched_batch_size=1000 → 每批约 275 万行，join_asof 内存爆掉
解法新建 scripts/finalize_enriched.py：临时把批大小改为 100 → 调 run_pipeline() → finally 恢复 1000
证据
[batch] enriched_batch_size 1000 -> 100
[pipeline] enriched rows=16487629
[batch] restored -> 1000
[done] 全量 enriched 重算完成
原执行记录第七节的第 3 步 SOP 会触发这个 OOM，不能直接照抄。正确姿势是走 finalize_enriched.py，或把 enriched_batch_size 先调到 100。已在原文档加警示。

八、剩余风险与限制（不要把回测结果当真实业绩）

  1. Docker 内存回落到 9.67 GiB（10378244096 bytes）。11-07 曾调到 15.44 GiB，本轮实测已回落。这是 OOM 反复出现的直接原因。若要跑全市场 5510 只的长历史回测，先把 Docker Desktop 内存持久调回 16 GiB 以上，否则继续限制 symbols 数量。全市场回测未验证
  2. 复权准确性未逐项审计：adj_factor 覆盖 27 个年份，但早期事件记录密度明显低于近年（2000 年 512 条 / 2025 年 4914 条）。回测证据链显示 daily_price_basis=qfq，早期前复权价是否准确没有逐笔核对。未验证
  3. ETF 未前复权：adj_factor_etf 为空，ETF 历史来自本机 TDX 同步。
  4. 基准数据只有一年：证据链 benchmark rows=366 / 2025-05-08 ~ 2026-11-06。长历史回测的「基准对比曲线」不完整，收益数字本身不受影响。
  5. 静态策略池前视偏差：七星175 的 52 只 ETF 池是当下定义，长历史回测含定义前视。
  6. enriched 少 18 行：指标窗口裁剪，正常但需知悉。
  7. 策略收益 -33.33% 只是验证样本：本轮目的是证明「数据能跑通」，不是评价策略好坏；80 只标的、单区间、无参数寻优。
已修订的流程规则：① 任何回填/补缺口写入后必须再跑一次 compact；② 长历史全量 enriched 重算必须先把 enriched_batch_size 调到 100；③ 判断数据是否完整一律用 DuckDB 直查，不看 /api/data/status 的 rows。
