一句话结论

好消息：这 7 个财务因子不需要改原版软件（上游）就能修好。

问题出在「我们自己加的外挂（二开补丁）」：它只为网页上的「个股核心指标」卡片计算了这些比率，却忘了回测程序那一条读取路径。补上这条路径即可，属于合规的二开改动，升级原版时不受影响。

这纠正了之前（2026-11-09 早些时候）的判断——当时以为是上游 financial_sync.py 缺数据、要改原版才能修。实测后发现：原始财务数据里「算这些比率要用的材料」其实 99.6% 都在，只是回测那一条读取线没吃到我们的换算。详见 ⚠ 更正。

⚠ 更正：之前判断错了

旧结论（错误）：「7 个财务因子失效是上游 financial_sync.py 没写 announce_date 和 6 个比率列导致的，必须改原版 / 本地补算 roe 无效，会被同步覆盖。」

新结论（实测后修正）：

  • 原始财务数据不是上游 financial_sync 写的，而是我们自己的「扶摇离线导入脚本」写入 data-local/financials/ 的；上游那个同步服务在本机根本没启用（财务数据源配置为空、也无相应套餐权限）。
  • 算这 7 个比率要用的「原材料」在 income / balance_sheet 表里 99.6% 都有（revenue / net_income / 总资产 / 净资产 / 总负债 缺失率均 <0.4%）。
  • 我们已有的二开补丁 overrides/financials_metrics_enrich.py 已经会算这些比率，只是它只接到了网页那条线（get_financial_df），没接到回测那条线（load_fundamental_snapshot）。
  • 所以修复点 = 把这条已经写好的换算，也接到回测读取路径上，并补一个「公告日」派生。完全在本项目的二开层内完成，不需要碰原版一行代码。

参考：本结论已同步回《因子自动挖掘 timeout 与绕过》文档 §5/§6/§9 的财务根因段落（见 未完成清单 第 1 项）。

根因：两道互相独立的缺口

回测因子之所以全为 null，是因为回测读取环节 load_fundamental_snapshot（app/backtest/fundamentals.py:44-78）对数据有两道硬性要求，当前两条都没满足：

要求（代码契约）当前现状后果
① 表必须含全部 7 个列：
bps, roe, gross_margin, net_margin, revenue_yoy, net_income_yoy, debt_to_asset_ratio
（fundamentals.py:59-64）		 metrics 表根本没有 roe / gross_margin / net_margin / revenue_yoy / net_income_yoy / debt_to_asset_ratio 这 6 个列（只有 bps，且 87.5% 为空）。 缺任一列 → 整个快照返回 None → 7 个因子全空。
② announce_date 不能全空，且逐行过滤掉为空的行（fundamentals.py:65-77） metrics 表 announce_date 43917/43917 = 100% 为空。 过滤后无一行存活 → 快照空 → 7 个因子全空。

为什么网页正常、回测却废？ 网页「核心指标」走 get_financial_df，被我们的二开补丁在读取时现场算出了这些比率；而回测走 load_fundamental_snapshot，它直接读原始 parquet 文件、绕过了补丁，于是看到的是「没算过、公告日全空」的原始数据。

项内容位置三态

⑤ bps（每股净资产）推导补全（覆盖 87.5% → 0.3%）

项内容位置三态

为什么不用「直接改数据文件」那种本地补丁

  • 读路径绕过、补了也白补：回测直接读 parquet 原始文件，任何手改 metrics 表都绕不开「缺列 + 公告日空」的契约；且我们已有补丁是「读取时换算、不改原文件一个字节」，正道是让回测也走这条换算线，而不是去涂改原始数据。
  • 重导会覆盖：若日后重跑扶摇离线导入，手改的数据会被覆盖；而读路径补丁是「每次读取现场算」，永不丢失。
  • 违背二开铁律：直接改 data-local/financials/metrics/part.parquet 属于改数据真源，升级/重导后状态漂移、难追溯；二开层包装才是可回滚、可审计的做法。
